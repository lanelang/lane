## Description
A `handle` expression whose value is discarded is deleted entirely: the handled
expression never runs and the handler never fires, with no diagnostic. Both
execution tiers reproduce it.

```lane
fn discarded(f : () -> Unit ! Probe) -> Unit ! Io {
  handle f() with {
    ping(resume) => { println("HANDLED") resume(()) }
  } final _v { () }
  ()                      // handle is in statement position: nothing prints
}
```

Measured scope. Only the arm and final contributions are lost:

| case | result |
| --- | --- |
| plain `Io` call in statement position | preserved |
| statement-position `handle`, arm performs `Io` | silently dropped |
| statement-position `handle`, final performs `Io` | silently dropped |
| handled expression itself performs `Io` | preserved |

The value disappears between the `buslane.monadic-lifted` and
`buslane.core-optimized` stages, at the dead-let rule in
`core_opt/simplify.mbt`:

```
if count_value_uses(body, value) == 0 &&
   expression_has_empty_effect(facts, original_initializer) { body }
```

Every layer that computes the residual computes it correctly:
`typecheck/handler.mbt` unions `arm_effect_contributions`, buslane's
`synthesize_handle` pushes the final and each arm effect, and
`effect_lowering/core/synthesis.mbt`'s `synthesize_install` unions body
residual, final latent, and every arm latent effect.

The loss happens because `core_opt.optimize` runs on the program *after* CPS
(`executable/elaborate.mbt:94`), where `Install` no longer exists. The install
has become an ordinary call `f_cps(dict, k)`. `rewrite_type` gives `f_cps` the
latent effect `residual_effect_part(f's own effect)`, which is correct for `f`
itself: `f : () -> Unit ! Probe` performs an algebraic effect that CPS delivers
through the dictionary, so its row is legitimately empty. The `Io` comes from
the **arm closures inside `dict`**, which `f_cps`'s type cannot describe.

So the invariant "a Buslane effect row over-approximates runtime effects" holds
before CPS and silently stops holding after it. Bug A is the first observed
consequence; any later analysis keyed on rows would be misled the same way.

## Design
Give the CPS'd type an effect parameter for the residual, so the row keeps
telling the truth after CPS.

`f_cps` genuinely *is* effect-polymorphic in what its dictionary does: one
definition is installed at several sites with different arms. A per-function
concrete latent effect cannot express that; an effect parameter can, and Lane
already has `Effect Variable` and `Effect Row Unification`.

Two facts make this narrower than it first appears.

The mon-effect branch of `rewrite_type`
(`cps/context_schema.mbt:235`) already generalises the CPS'd type, introducing
`Forall([%answer], ...)` with a fresh `%answer` type parameter. Adding a
`%residual` effect parameter is the same move a second time;
`Kind::Effect` and `define_type_parameter(name, Effect)` already exist and are
used elsewhere.

The dictionary type is already parameterised by the residual:
`context_argument_types` threads `residual_effect` into
`self.dictionary(effect, residual_effect)` and into the continuation type. Today
it passes the declaring site's concrete residual; the change is to pass the
variable instead.

### Sketch

In the `is_mon_effect` branch of `rewrite_type`, alongside `%answer`:

```
let residual_parameter = self.metadata.define_type_parameter("%residual", Effect)
let residual = @buslane.Effect::Parameter(residual_parameter)
Forall([answer_parameter, residual_parameter],
  Function(context_types(effect, answer_type, residual)
             + rewritten_parameters
             + [continuation_type(rewritten_result, answer_type, residual)],
           answer_type,
           residual))
```

At the install site, `lower_cps_install` already holds
`install_facts.effect`, the residual that `synthesize_install` computed
correctly. Instantiate with `residual_effect_part(install_facts.effect)`, which
keeps `Io` and External terms and drops still-algebraic ones, since those are
delivered to an enclosing dictionary rather than performed.

With that, the dropped term in the reproduction synthesises with `{Io}` and the
dead-let rule leaves it alone, with no change to `core_opt`.

### Decisions for review

1. **Binder placement.** Put `%residual` in the same `Forall` as `%answer`,
   ordered `[%answer, %residual]`. One binder site and one instantiation site,
   matching the existing shape. The alternative, a separate outer `Forall`,
   keeps existing single-binder patterns matching but introduces two
   generalisation points for one ABI.

2. **Instantiation form.** `TypeApply(callee, [TypeArgument(answer),
   EffectArgument(residual)])`, extending the existing type application rather
   than adding a second one.

3. **Recursive residuals.** An arm may itself install a handler, so an install's
   residual can mention the enclosing function's `%residual`. Reject a residual
   that contains its own binder, mirroring `RecursiveHandlerResidualEffect`
   which `typecheck/handler.mbt:123` already raises at the source level, rather
   than attempting a fixpoint.

4. **Dictionary types must become residual-parameterised.** Found by attempting
   the change: `define_dictionary_header` monomorphises the dictionary type per
   *concrete* residual. `DictionaryCpsSchema::dictionary(effect, residual)`
   looks a header up by `effects_definitionally_equal` on the residual and mints
   a new type when none matches, even naming it with an `%io` suffix. Feeding it
   a residual *variable* mints a fresh dictionary type on every `rewrite_type`
   call, and the CPS pipeline aborts; verified experimentally.

   **Settled, and it inverts this design.** `git log -S '"%io"'` points at
   `e36981b5`, whose issue ISS-202 is titled "Preserve and erase residual
   non-monadic effects". Its design reads "Preserve residual `Io` on direct and
   CPS-transformed callable and continuation types", and its close notes say it
   implemented "residual-aware CPS callable and dictionary schemas".

   So per-residual specialisation is not an obstacle to remove. It is the same
   mechanism this issue wants, built by monomorphisation instead of
   polymorphism, and applied to only one of the two sources of residual:

   | source of residual | ISS-202 | observed |
   | --- | --- | --- |
   | the handled expression's own effect | covered by design | works |
   | handler arm effects | not considered | dropped |
   | final branch effects | not considered | dropped |

   The install site's residual is *concrete*: `lower_cps_install` already holds
   `install_facts.effect`. Monomorphisation therefore applies directly, and no
   effect variable is needed. The likely-correct design is to extend the
   existing residual-aware scheme to account for the install-site residual,
   rather than to introduce `%residual` and replace specialisation with
   parameterisation.

   Cost is the usual monomorphisation trade: one CPS form of a function per
   distinct residual it is installed under. `dictionary()` already mints headers
   on demand, so that path is open.

   Decisions 1 and 2 above are therefore superseded pending a revised sketch;
   decision 3 still stands.

### Blast radius

Three sites destructure the current single-binder shape and must accept two:

- `cps/abi.mbt:187`
- `cps/argument_adaptation.mbt:45`
- `cps/argument_adaptation.mbt:135`

Downstream passes carry the parameter through: `resolve_open_contexts`,
`lift_monadic_continuations`, and `erase_residual_effects`, which already erases
residual effects before bytecode and should erase this parameter with them.

### Non-goals

No change to `core_opt`; its gate becomes sound once rows are honest again. No
change to the source language or to `Residual Effect Set` as documented; this
restores the lowering to what `CONTEXT.md:588` already specifies. Bug B in the
same report is not a Lane defect and is excluded.

## Close Notes
Selective CPS now binds an effect row variable for the residual next to the
answer type, and every call site instantiates it with the residual it is itself
running under. The `%io` dictionary specialisation is gone: one dictionary per
effect again, parameterised over its residual.

The corrected direction in decision 4 turned out to be wrong, and reading
`e36981b5` is what showed why. ISS-202 built residual awareness by
monomorphisation because the install site's residual is concrete, and that works
for a definition compiled in the same place it is installed. It cannot work in
general: `f`'s CPS form is produced once, from `f`'s own declared effect, while
the dictionaries handed to it are built at each install. Extending
monomorphisation would mean one CPS form of every function per residual it is
ever installed under, decided by whole-program knowledge that a parameter of
function type or a separately compiled module does not have. The measured
symptom was exactly that mismatch: `body`'s CPS form matched on the base
`Probe%dictionary` while the install passed it a `Probe%dictionary%io`, so both
the row and the dictionary type were wrong and only the row was observable.

So decisions 1 and 2 stand after all, in the form they were first written.

Shape. For `f : A -> B ! E` with `E = M ∪ R`:

```
forall answer, residual. (dict_M<answer, R'>, A, (B) -R'-> answer) -R'-> answer
  where R' = R ∪ residual
```

Keeping `R` inside `R'` rather than using `residual` alone is what makes
instantiation collapse: a call site passes its own `R'`, and since source typing
already makes a callee's residual a subeffect of its caller's, `R ∪ R'_caller`
is `R'_caller`. No subeffecting is needed at the ABI.

Three things fell out that the design had not anticipated:

- **The distinction had to be modelled, not inferred.** `is_mon_effect` reads
  every effect parameter as still needing lowering, which is right for a source
  effect parameter and wrong for this one, and `validate_mon_trans_output`
  rejects effect parameters and effect arguments outright. Both are load-bearing
  invariants and neither should be weakened by phase or by name. Buslane already
  classifies effect *declarations* with `EffectFlavor`, so effect *parameters*
  now carry the same field, `Algebraic` by default exactly as `define_effect`
  does. The three effect-lowering predicates read it the same way they already
  read a declaration's flavor, and the validator keeps rejecting algebraic
  parameters and algebraic effect arguments while allowing residual ones.

- **Residual computations are CPS'd callables too.** The frames built for a
  handler's `resume` were `Forall([answer], ...)` while the generic call path
  instantiated two arguments, so nested handlers failed to verify. They bind a
  residual now, which removes the exception rather than adding a case for it.

- **Recursive residuals never arise.** Decision 3 planned to reject a residual
  containing its own binder, mirroring `RecursiveHandlerResidualEffect`. An
  install site's residual is concrete, so the instantiation is always a closed
  substitution and there is nothing to reject. An arm that installs its own
  handler is covered by a regression test.
