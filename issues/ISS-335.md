## Description
LoisVM Bytecode is persisted and decoded across a trust boundary, but decoding
only validates selected function-body metadata. Instructions, slot identities,
runtime representations, initialization/dataflow, ownership, and call shapes
remain trusted. The new float-to-string instructions extend that unverified
surface.

## Design
Define a package-owned bytecode verifier that validates the complete decoded
`BytecodeImage` before it is returned to consumers. It must check referential
integrity and instruction contracts using the image's layout, function, block,
slot, constant, and import metadata. Decoder structure checks remain decoder
responsibility; semantic bytecode validity has exactly one verifier owner.

## Acceptance Criteria
- [x] Every persisted Bytecode instruction has a verifier rule for identities and runtime representations.
- [x] Function/block/slot/control-flow references and statically known callable signatures are checked.
- [x] Invalid decoded and directly constructed images return structured errors rather than reaching interpreter or Wasm lowering.
- [x] Black-box tests cover representation, dataflow, ownership, direct-call, CFG, global, and decoder boundaries; private codec symmetry covers every instruction constructor.
- [x] Valid compiler-produced images still round-trip and pass interpreter/JIT gates.
- [x] LoisVM context documentation defines verified bytecode and the dynamic indirect-target boundary.

## Close Notes
`loisvm/bytecode` now owns one semantic verifier with structured image,
function, block, instruction, and terminator provenance. Binary decoding,
interpreter loading, and Wasm compilation all call that verifier. It checks
identifier ranges, metadata legality, instruction representation contracts,
object shapes, direct-call ABI, CFG edges, definite initialization, global
initialization, and linear owner flow without treating trivial values as moved.

The integration exposed a VM CFG optimizer defect: scalar constant folding
could remove a layout value still named by `erased_companion` metadata. The
optimizer now treats companion identity as an implicit use, with a focused
white-box regression; compiler-produced images then pass verification.

Verified on 2026-08-05 with bytecode 23/23, interpreter 35/35, Wasm 74/74, and
the full native suite 1548/1548.
