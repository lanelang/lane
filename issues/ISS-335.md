## Description
LoisVM Bytecode is persisted and decoded across a trust boundary, but decoding
only validates selected function-body metadata. Instructions, slot identities,
runtime representations, initialization/dataflow, ownership, and call shapes
remain trusted. The new float-to-string instructions extend that unverified
surface.

## Design
Define a package-owned bytecode verifier that validates the complete decoded
`BytecodeImage` before it is returned to consumers. It must check referential
integrity and instruction contracts using the image's layout, function, block,
slot, constant, and import metadata. Decoder structure checks remain decoder
responsibility; semantic bytecode validity has exactly one verifier owner.

## Acceptance Criteria
- [x] Every persisted Bytecode instruction has a verifier rule for identities and runtime representations.
- [x] Function/block/slot/control-flow references and statically known callable signatures are checked.
- [ ] Invalid decoded and directly constructed images return structured errors rather than reaching interpreter or Wasm lowering.
- [x] Black-box tests cover representation, dataflow, ownership, direct-call, CFG, global, and decoder boundaries; private codec symmetry covers every instruction constructor.
- [x] Valid compiler-produced images still round-trip and pass interpreter/JIT gates.
- [x] LoisVM context documentation defines verified bytecode and the dynamic indirect-target boundary.
- [ ] Semantic value-kind documentation matches the current bytecode model and
      no longer describes the removed abstract-reference category as crossing
      the persistent boundary.
- [ ] Dataflow proves exact object shape before tag, field, capture, or witness projection and preserves the proof through ownership transfer and erasure boundaries.
- [x] Decoder semantic actions only decode framing and tagged fields; directly constructed and decoded images use the same verifier-owned Char, UTF-8, runtime-symbol, and metadata rules.
- [x] Direct and indirect callable ABI checks reject incompatible concrete value
      shapes consistently without admitting cross-category casts.
- [ ] Erase/Unerase transfers the proven source `ObjectShapeId`, or rejects an
      attempt to unerase into incompatible destination metadata; it never
      invents provenance from the destination slot alone.
- [ ] A `LayoutOperand::Witness` used to construct an object is proven to
      describe that instruction's `ObjectShapeId`; a mismatched dynamic layout
      is rejected before either production backend can allocate the object.

## Close Notes
`loisvm/bytecode` now owns one semantic verifier with structured image,
function, block, instruction, and terminator provenance. Binary decoding,
interpreter loading, and Wasm compilation all call that verifier. It checks
identifier ranges, metadata legality, instruction representation contracts,
object shapes, direct-call ABI, CFG edges, definite initialization, global
initialization, and linear owner flow without treating trivial values as moved.

The completed image now carries a semantic value kind beside physical
representation and cleanup. Data values name a nominal family, Environment
values name an exact object shape, and dataflow refines a Data family to an
exact constructor shape before projection. Ownership transfer and erasure
preserve that provenance. Constants and runtime-import names are validated by
the same verifier for decoded and directly constructed images.

Callable ABIs use the same complete value shape. Explicit abstract reference
parameters bind consistently across one call; they cannot turn a ByteSequence
argument into a Data result. The interpreter checks dynamically selected
targets against that relation, and Wasm indirect calls use a compatibility
matrix derived from it. The linked-program schema is 11.

The integration also preserved the earlier VM CFG companion-liveness fix and
verified both higher-kinded Data results and erased-to-scalar effect-handler
results at their shared generic-call boundary.

Verified on 2026-08-05 with targeted bytecode/interpreter/Wasm tests 150/150,
generic/effect conformance tests 29/29, and the full native suite 1570/1570.
