# ISS-281: Make the explored Wasm stage the module that is actually emitted

## Description
The `wasm` stage of an Explore Report does not round-trip into a valid module,
so the IR explorer's view of the backend cannot be trusted or handed to other
tools.

Reproduction: run `lane explore -o report.html FILE:ENTRY`, take the `wasm`
stage text, and parse it with `wasm-tools`. The text is complete, carries no
truncation marker, and passes syntactic parsing, but fails validation:

```
examples/valid/78_structural_derivation.lane
  type mismatch: values remaining on stack at end of block  (offset 43090)
examples/valid/83_utf8_string_char_i32.lane
  type mismatch: expected i64, found i32                    (offset 2477)
```

Both programs run correctly through `lane run`, which executes generated
WebAssembly. Every Wasm engine validates before executing, so the emitted module
is necessarily valid. The rendered text is therefore not the emitted module: the
explorer's Wasm printer is a separate path from emission, and it is not
faithful.

`wat2wasm` from wabt rejects the same text earlier, on `(table ... (ref.null
func))` and on `tag`, because it predates those proposals; `wasm-tools` accepts
the syntax and rejects the types, which is the meaningful signal.

This was found while trying to attribute the slowdown in ISS-280 to either our
code generation or the Wasmoon engine. Compiling the same module with a second
engine is the decisive experiment, and this defect blocks it.

## Design
Render the stage from the module that is actually emitted rather than from an
independent printer: emit the module, then disassemble those bytes for display.
That makes the stage faithful by construction and removes a second
representation that can drift.

If a separate printer must stay, it needs a round-trip check: emit, print,
re-parse, validate, and compare against the emitted bytes.

Exposing the emitted bytes is worth considering alongside this, since attributing
backend behaviour to an engine requires feeding the real module to that engine.

## Acceptance Criteria
- [x] The `wasm` stage text of an Explore Report parses and validates as a
      WebAssembly module.
- [x] A test covers round-tripping the stage for a program whose module is
      non-trivial, including one with `tag` and a table initializer.
- [x] The emitted module can be obtained for external analysis.

## Close Notes
The diagnosis in the description was wrong about where the second
representation lived. `@wasm_compiler.compile` returns one `Module`, and both
consumers read it: `@wasm_encoder.encode` for the bytes an engine runs, and
`module_to_wat` for the explored text. `compile` validates before publication,
so the `Module` was always good. The printer was rendering it incorrectly.

Root cause: `write_instruction` in
`modules/loisvm/wasm/compiler/wat.mbt` ended its match with a fallthrough that
rendered any unhandled instruction as a WAT comment, `(; unsupported X ;)`. A
comment is syntactically valid and is discarded on re-parse, so the instruction
vanished, the text still parsed, and only type validation noticed. The existing
`wat_test.mbt` checked parsing only, on an empty function body, so it passed
throughout.

Exactly two emitted instructions were unhandled: `I32Store8`, which appears
three times in the runtime helpers of every module and therefore broke every
program, and `I64ExtendI32S`. Both are now printed. The fallthrough now emits
`unsupported.instruction`, which no parser accepts, so a future gap breaks the
text instead of quietly changing the module it claims to show.

`wat_test.mbt` now round-trips print, re-parse, and validate across a minimal
module, boolean branches, dense tag switches, reducible loops, and a direct
call, rather than parsing one empty body.

Verification:
- `moon check --warn-list +73` clean; `moon test --target native` 1342 passed;
  `tools/check-lane-run-examples.sh` passes.
- External confirmation: the `wasm` stage of both
  `examples/valid/78_structural_derivation.lane` and
  `examples/valid/83_utf8_string_char_i32.lane` now pass `wasm-tools parse` and
  `wasm-tools validate`, with zero `unsupported` markers. Both previously failed
  validation.

This unblocked the experiment ISS-280 needed. `wasmtime compile` handles the
example 78 module in 0.06s while Wasmoon takes 58s, which moves that issue's
prime suspect. Recorded there.
