# ISS-352: Preserve fatal execution as a typed user-facing outcome

## Metadata
- Type: bug
- Status: closed
- Priority: 2
- Labels: area/lane, area/loisvm, runtime, diagnostics, fatal-errors, public-api, tests, agent
- Assignee: codex
- Created: 2026-08-10
- Updated: 2026-08-10
- External ref: modules/loisvm/runtime/core.mbt, modules/loisvm/runtime/host_sdk.mbt, modules/lane/run.mbt, modules/lane/diagnostic.mbt

## Description
The source-level `Basic.Io.panic` contract terminates execution intentionally,
but the runtime currently reports it as the same generic host-import failure
used for accidental embedding errors. The Lane command then erases the complete
`ExecutionError` with `Repr` and exposed the internal constructor text:

```text
RuntimeImportFailure(symbol="panic", message="boom")
```

This is a valid internal debugging representation, not an appropriate language
diagnostic. It describes an intentional fatal operation as an import defect,
leaks the LoisVM model, and prevents the final renderer from classifying runtime
failures without parsing a string.

## Design
Keep one typed execution-failure boundary while giving intentional fatal
termination a distinct case. The implemented fatal-control RFC now produces
that case from the compiler-owned `Fatal` terminator; no compiler or CLI layer
infers fatality from a symbol, and no public host panic binding remains. Both
production backends preserve the classification as
`ExecutionError::Fatal(message)`.

The Lane command must retain `ExecutionError` through `CliError` and translate
it only at the command-report boundary. Fatal execution receives a dedicated
user diagnostic, while ordinary runtime-import failures continue to include the
offending symbol. Update ADR-0130 to describe the classification without
introducing a recoverable Lane effect, a `Result`, or a second control channel.

## Acceptance Criteria
- [x] Compiler-owned `Fatal` execution produces a typed fatal outcome without checking a Runtime Import symbol.
- [x] Interpreter and Wasm/JIT executions return the same `ExecutionError::Fatal(message)` and never run the continuation.
- [x] Ordinary host binding failures remain `RuntimeImportFailure(symbol, message)` in both backends.
- [x] `lane run` and `lane run --no-jit` render fatal execution as a dedicated diagnostic containing the supplied message.
- [x] The fatal CLI diagnostic does not expose `RuntimeImportFailure`, `ExecutionError`, LoisVM constructor syntax, or the implementation symbol.
- [x] `CliError` retains structured execution failures until the final diagnostic rendering boundary.
- [x] ADR-0130 and the host SDK contract describe the typed fatal classification and unchanged cleanup semantics.
- [x] Black-box runtime and executable-command regressions cover fatal and ordinary import failures.
- [x] `moon info`, `moon fmt`, `moon test --target native`, the Basic check, and the integration gate pass.

## Notes
- 2026-08-10: Reproduced with the shipped Basic API. The current command emits E6013 with `reason: RuntimeImportFailure(symbol="panic", message="boom")` in both production modes.

## Close Notes

- 2026-08-10: Added an explicit fatal classification to the public host-call
  failure channel and preserved it as `ExecutionError::Fatal` across the
  interpreter and Wasm/JIT backends. The ordinary failure case and its symbol
  remain unchanged.
- 2026-08-10: Lane now retains the typed execution error until command-report
  rendering. Fatal execution renders as `E6017: Lane program panicked` with the
  source message and no runtime constructor or import symbol.
- 2026-08-10: Verified the fatal and ordinary black-box backend regressions,
  both CLI execution modes, all 1,599 native tests, the integration gate, and
  the Basic check with the current release build.
- 2026-08-10: The fatal-control RFC removed the interim
  `RuntimeBinding::fatal_string` transport. `ExecutionError::Fatal` and the CLI
  diagnostic remain the public outcome, now sourced directly from verified
  `Fatal` bytecode in both backends.
