# ISS-310: Scope top-level lets sequentially in the verifier

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: area/buslane, correctness, verifier, interpreter, agent
- Assignee: -
- Created: 2026-08-03
- Updated: 2026-08-03
- External ref: modules/buslane/verify.mbt, modules/buslane/interpreter/evaluate.mbt

## Description
`verify_terms` (verify.mbt:316) pushes every top-level id into scope before
verifying any term, so `Let(a, Ref(a))` and forward references between plain
lets verify clean (measured). The interpreter's contract is the opposite:
"top-level `let` terms are evaluated in order" (evaluate.mbt:6), so both
programs raise `UnboundValue` at runtime — a verified program failing the
reference evaluator breaks the chain-of-trust invariant that verification
implies evaluability.

The rule is also non-uniform: `TopTerm::LetRec` exists precisely to admit
recursion, and pays for it with the `is_direct_function_implementation`
restriction on every rhs. Plain `Let` currently gets recursion for free with no
restriction, making LetRec's restriction meaningless as a law.

## Reproduction
```moonbit
let a = metadata.define_value("a", Value, Primitive(Unit))
let b = metadata.define_value("b", Value, Primitive(Unit))
assert_true(verify_program({ metadata, terms: [Let(a, Ref(a))] }).is_ok())
assert_true(verify_program({ metadata, terms: [Let(a, Ref(b)), Let(b, Literal(Unit))] }).is_ok())
// Both raise UnboundValue in the reference interpreter.
```

## Design
Build the top-level scope sequentially: a plain `Let` verifies its initializer
against the scope of strictly earlier terms, then joins scope; a `LetRec` group
joins scope before its own rhs verification (recursion stays confined to the
construct built for it). External terms join as encountered.

## Acceptance Criteria
- [x] Self-referential and forward-referencing plain top lets produce diagnostics.
- [x] LetRec groups still verify mutual recursion.
- [x] A test pins verify/interpret agreement: every top-term shape the verifier accepts evaluates without UnboundValue.

## Close Notes
The top-level scope is now built term by term, but split by evaluation time
rather than made strictly sequential. `ValueScope` carries `values` (bound by
the time this expression runs) and `deferred` (top-level bindings that come
later); `ValueScope::entered`, used when descending into a function body,
promotes deferred to bound. That mirrors the reference interpreter exactly: a
closure captures the global environment and resolves names when called, by
which point every top-level term is bound, while anything evaluated at binding
time can only reach what precedes it. A `LetRec` group joins scope before its
own right sides, since its closures are installed before any of them run.

Plain sequential scoping was implemented first and measured wrong: it rejects
the real pipeline, because elaborate emits all functions as one leading
`LetRec` and all value lets after it (`collect.mbt:374`), so every function
body referencing a top-level value became an error. Those programs run
correctly, so the rule — not the pipeline — was at fault.

The measurement also found a genuine ordering defect: effect specialization
appended its specialized instances as a trailing `LetRec`, after retained
value initializers that call them (`let handled_value = handle_log(...)()` in
the effect-conformance corpus). Specialized definitions are function
implementations, so the group installs closures without evaluating; it now
leads the program, which is where a binding that eager initializers may call
belongs. Two test fixtures asserting the old term order were updated, and one
`elaborate_test` fixture that genuinely forward-referenced a function from an
eager initializer was reordered.

Known limit, not covered by a syntactic scope rule: a top-level initializer
may still call a function whose body reads a later binding, because a body
also runs *during* binding, not only after it. Measured end-to-end through
`lane run` — the program reaches LoisVM and fails with an internal runtime
error — and filed as ISS-317 with the reproduction. Catching it needs
initializer-order call-graph analysis in the checker, where the source span
still exists; the syntactic rule catches the direct cases this issue reported
and stays sound for what it claims.

Regressions: the issue's two reproductions plus the accepted ordering, a
function body reaching a later binding, mutual recursion inside one `LetRec`,
and — in the interpreter package — one program using every top-term shape and
every reference form the verifier admits, asserted to verify clean and then
evaluate without `UnboundValue`. Red/green measured: the reproduction test
fails against the pre-fix verifier.

Verified: `moon check --target native --warn-list +73` clean (0 warnings);
`moon test --target native` 1451/1451; examples gate exit 0 against the
pinned fixture; no `.mbti` drift.
