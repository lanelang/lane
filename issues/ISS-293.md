# ISS-293: An effect parameter's companion cannot stand for one dictionary type

## Description
`examples/valid/45_async_effect.lane` produces two `TypeMismatch` after
monadic-lift. Both compare a CPS'd callable passed as an argument against the
parameter it is passed to. The expected type is a callable whose dictionary sits
at the *enclosing* function's answer and residual:

```
Forall([%answer#404, %residual#405],
  Function([ Schedule%dictionary<%answer#414, %residual#415>, ... ],
           Parameter(%answer#404), Parameter(%residual#405)))
```

while the actual binds its own and uses them throughout:

```
Forall([%answer#52, %residual#53],
  Function([ Schedule%dictionary<%answer#52, %residual#53>, ... ],
           Parameter(%answer#52), Parameter(%residual#53)))
```

The two are each well formed in their complete enclosing declarations, but they
disagree about which pair the dictionary belongs to. Neither fragment is
justified as "more general": their quantifiers vary different dimensions, so
the complete outer types must be compared in both directions with
`type_is_consumable_as` before claiming any relation. `rewrite_type` produces
the second shape for an effectful function type.

`examples/valid/37_coroutine_scheduler.lane` reports the same disagreement,
nested one level further: there the dictionary's own type argument is another
dictionary sitting at a pair the callable does not bind. After ISS-292 removed
everything else, these two programs report two of these each and nothing
else.

This started as "the binders and the parameter values come from different
`rewrite_type` generations", which is what the uniques suggest. Instrumenting
the pass ruled that out. Across every `examples/valid` program:

- no CPS callable construction site — `lower_cps_function`,
  `lower_cps_effectful_result_call`, `UnhandledFrame::fresh_frame`,
  `adapt_direct_argument_to_cps` — builds a callable whose parameter values
  mention an answer or residual other than the binders it is about to bind;
- `rewrite_type`'s monadic branch never produces a type with a free `%answer`
  or `%residual`;
- no type committed through `store_cps_value_type` has one either.

So neither expression construction, type construction, nor the commit path
leaks a binder. The parameter is not free in its scope, and the uniques being
from different generations is a consequence of allocation order rather than
evidence of a capture.

Instrumenting the call reporting the mismatch names the callee in both
programs: `%operation`, the match binder for a dictionary field. So the expected
type is an operation's payload type, taken from `instantiate_dictionary`, and
the two programs share one cause.

Both effects involved are effect-generic, and both have an operation whose
payload is a function mentioning the effect parameter:

```lane
effect Async[E : Effect]     { suspend[A](((A) -> Unit ! E) -> Unit ! E) -> A }
effect Coroutine[E : Effect] { spawn[A](() -> A ! { Coroutine[E], E }) -> Unit }
```

`define_effect_companions` gives the effect parameter `E` a `Type`-kind
companion `E%context`, standing for the dictionary that carries `E`. Rewriting
the operation's payload produces a nested CPS'd callable that binds its own
answer and residual and holds `E%context` in its parameter list:

```
Forall([a2, r2], Function([ ... Parameter(E%context) ... ], a2, r2))
```

`instantiate_dictionary` then substitutes `E%context` with
`packed_context_type(e, answer, residual)` at the *instantiation site's* answer
and residual, and that substitution reaches inside the nested `Forall`. The
callable ends up binding `a2, r2` while the dictionary in its parameter list
sits at the instantiation site's pair — exactly the expected type in the
mismatch. The argument, built by `lower_cps_function`, is at its own pair
throughout.

A companion is one `Type`, so it can name a dictionary at exactly one answer and
residual. It is used at two: the instantiation site's, and each nested
callable's. Nothing chose wrongly; the representation cannot express both.

## Design
A companion has to vary with the answer and residual of whatever callable uses
it, which means it is not a type but a function from those to a type.

Buslane can already say that. `Kind::Function(Array[Kind], Kind)` exists, and
`TypeLambda` and `Apply` are the introduction and elimination forms. A companion
becomes a parameter of kind `Function([Type, Effect], Type)`, every use applies
it to the answer and residual in scope there, and the instantiation site passes
a `TypeLambda` over the dictionary it means. The nested callable applies the same
companion to its own pair, and the outer dictionary applies it to the
instantiation site's, from one argument.

The alternative — forbidding a nested callable from binding its own answer and
residual, so that only one pair is ever in play — makes an operation payload's
callable non-generic in its answer type. That contradicts **Answer-Type CPS**,
whose whole point is that a CPS'd callable is polymorphic in its answer.

This ABI rule belongs in `CONTEXT.md` beside **Answer-Type CPS**. Unifying each
callable occurrence around one `CpsCallableShape` is an independent refactor
tracked by ISS-294. Making declaration metadata single-owned and checking a
lowered RHS by directed consumability is tracked by ISS-295. Neither is part of
the root-cause fix here, and no binder-identity defect is assumed.

## Acceptance Criteria
- [ ] An effect parameter's companion can name the dictionary it stands for at
      more than one answer and residual, and `CONTEXT.md` says how.
- [ ] A CPS focused test covers a higher-order effectful parameter, a nested

      it pins the resulting dictionary-pair distinction directly rather than
      looking for a free binder.
- [ ] `examples/valid/45_async_effect.lane` and

## Notes
- 2026-08-02: The higher-kinded companion was implemented far enough to confirm
  it is the right fix and to map its cost, then reverted rather than landed,
  because it does not reach a green tree yet.

  What it achieved: **every** `examples/valid` program verifies both on the
  effect-lowering input and after monadic-lift, and all 85 still run correctly.
  Both failures this issue is about are gone. The change inside the CPS package
  is small — the companion's kind, one helper to apply it, one to abstract over
  it, and three supply sites that no longer need an answer at all.

  What it costs elsewhere. An erased value stops being written `Parameter(p)`
  and becomes `Apply(Parameter(p), [answer, residual])`, and a companion
  argument becomes a `TypeLambda`. Nine sites in `loisvm_lowering` test for the
  old shape and have to accept both: `slots.mbt` twice plus
  `result_representation`, `type_adaptation.mbt` four times, `value_erasure.mbt`
  three times, and one each in `calls.mbt`, `closures.mbt`, `expressions.mbt`,
  `match_data.mbt`, and `function_cfg.mbt`. Two rules make those uniform and are
  worth stating rather than repeating:

  - A companion's layout does not depend on the arguments it is applied to. The
    dictionary it denotes is a heap object at every answer and residual, so one
    witness per parameter still describes every use. `requires_layout_witness`
    accepts `Function(_, Type)` for the same reason.
  - A type-level function's layout is its body's, so `slot_metadata`,
    `result_representation`, `layout_witness`, and `erase_value` follow through
    a `TypeLambda`.

  Where it stopped: 1351 of 1355 tests. Two are this issue's own assertions
  about the companion's kind and use, which the change is meant to alter. The
  other two are `effect_polymorphic_callback_wbtest.mbt` on the *pure* callback
  shape only — the effectful one passes — failing with "generic argument
  representation does not match its type" in `erase_value`. An effect
  instantiated at `{}` packs to `Primitive(Unit)`, so the companion argument is
  `TypeLambda([a, r], Unit)`, and erasing through it reaches a slot whose type
  says `Unit`. Following the body is not enough there; the next step is to
  understand what that value is rather than add another case.
- 2026-08-02: Retitled and re-scoped after instrumenting. The original premise —
  that a binder escapes its owner — is disproved by the three measurements in
  the description. `CpsCallableShape` on its own would not have fixed this
  example, because every site it would unify is already self-consistent. It is
  still worth building, as the thing that keeps both sides of a call on one
  rule, but the rule has to be decided first or the refactor has nothing to
  enforce.

  Priority dropped from 0 to 1: ISS-292 is unblocked and independently
  verifiable, this one now starts with a design question.
- 2026-08-02: Root cause found and priority back to 0. Instrumenting the failing
  call named `%operation` as the callee in both programs, which placed the
  expected type in `instantiate_dictionary`, and from there the companion
  substitution accounts for both shapes. It is not a rule nobody wrote down; it
  is a representation that cannot hold the answer.

  This also settles why the earlier free-binder probes came back clean. The
  pair in the expected type is bound — by the enclosing dictionary's own
  quantifier. Printing a parameter type in isolation is what made it look free.
