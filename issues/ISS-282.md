## Description
`examples/valid/78_structural_derivation.lane` takes about 57s against the
fixture runner's 60s timeout, leaving roughly 5% of headroom. Any change that
adds a few percent of compiler overhead pushes it over, and the failure reads as
a timeout in the example rather than as a cost added elsewhere.

This already happened. While narrowing the interface closure in ISS-279, a first
implementation that walked each interface three times cost about 3.5% and turned
that fixture red. The report gave no indication that the cause was a small
uniform overhead rather than something wrong with structural derivation, and
distinguishing the two took a baseline run with the change stashed.

The underlying slowness is ISS-280. Until that lands, the gate's signal for
every unrelated change is degraded, and the whole smoke run is dominated by this
one example.

## Design
Make the fixture report attributable rather than just longer. Options worth
weighing:

- Record a per-case expected duration and report the observed one, so a timeout
  says how far past the budget it went and whether other cases also drifted.
- Give a known-slow case an explicit larger timeout with a comment naming
  ISS-280, so the budget is a stated decision rather than a shared default that
  one case happens to sit against.
- Report total and per-case timings, so a uniform slowdown is visible as a
  pattern rather than as one failure.

Raising the shared timeout alone is not enough: it hides the drift without
making the next misattribution any less likely.

Close this when ISS-280 removes the underlying cost, if the headroom problem
disappears with it.

## Acceptance Criteria
- [ ] A fixture timeout reports the observed duration against its budget.
- [ ] A uniform compiler slowdown is distinguishable from one slow example.
- [ ] Any per-case timeout override names the issue that justifies it.
