# ISS-317: Derive initialization order from dependencies at value granularity

## Description
Lane already derives initialization order from dependencies and rejects cycles
at compile time — at module granularity. `LinkModuleIndex::visit`
(link/core.mbt:238) is a depth-first topological sort over imports that reports
`LinkImportCycle` when it finds a back edge. The same law is not applied inside
a module: `lower_top_terms` (collect.mbt:364) emits value lets in declaration
order, so source position, not dependency, decides when a value is initialized.

The inconsistency is observable. Name resolution is order-independent (a
function may read a value declared later — `examples/valid/01_top_level_
forward_function_value.lane` relies on it), but evaluation is order-dependent,
so an initializer that calls such a function reads an unbound value. Measured
end-to-end through `lane run`:

```lane
pub fn read_later(n : I64) -> I64 {
  if n == 0 { later } else { read_later(n - 1) }
}
pub let eager : I64 = read_later(3)   // runs read_later NOW
pub let later : I64 = 7               // bound after
pub fn answer() -> Unit ! Io { if eager == 7 { println("7") } else { println("bad") } }
```

```text
error[E6013]: LoisVM execution failed
  reason: InternalRuntimeFailure(detail="Wasm instance-global lifecycle failure")
```

Moving `later` above `eager` makes the identical program print `7`. A
statically decidable ordering mistake reaches the user as a Wasm lifecycle
failure three layers below the source.

When the callee is small enough to inline, the core optimizer substitutes its
body into the initializer, the reference becomes eager, and ISS-310's verifier
rule catches it — as `error[E6011] ... UnverifiedProgram(stage="core
optimization", ... UnknownValue({index: 3}))`. A compiler-internal message for
a user error, and it vanishes as soon as the callee resists inlining.

Root cause: initialization order has no owner at value granularity. Three
components each assume part of it — elaborate emits functions then values in
declaration order, effect specialization prepends its specialized group
(ISS-310), and the Buslane verifier checks a scope rule — and none computes it.

## Design
Apply the module-level law at value granularity: initialization order is
derived from dependencies, and a cycle is a compile-time diagnostic. Source
position then carries no evaluation semantics at either granularity, matching
the order-independent scoping Lane already has.

Ownership: the checker computes it. It is the only place holding declaration
order, the reference graph, and spans, so it is the only place that can report
a cycle at the offending declaration. Elaborate consumes the result — it should
not re-derive anything.

The dependency edge is purely lexical, as in Go: a value depends on the names
its initializer references, transitively through the bodies of any functions
referenced. A cycle among functions is ordinary mutual recursion and stays
legal; only a cycle among *values* is the error. Higher-order flow needs a
stated approximation — treating any function value mentioned in an initializer
as potentially called is sound and may reject a program that only stores a
closure; adopt precision only if a corpus program measurably needs it, and
record the choice.

Prefer making the checked module's let-declaration order *be* the
initialization order, so every downstream consumer preserves the fact by
preserving list order, rather than adding a side table each stage must
remember to consult. Fall back to an explicit order only if a consumer
genuinely needs source order (diagnostics carry spans, so they do not).

The Buslane rule from ISS-310 stays exactly as landed: with a dependency
order, emitted terms satisfy it, and it becomes the backstop that catches any
stage that breaks the order.

## Close Notes
`CheckedSourceFile::initialization_order` (checked/initialization_order.mbt)
derives the order with the same depth-first walk the linker uses for modules,
one granularity down: nodes are the module's top-level values and functions,
edges are lexical references collected through the existing
`for_each_child_expr` traversal, and a back edge is a cycle only when the loop
contains an initialized value — a loop through functions alone is ordinary
mutual recursion and stays legal. `in_initialization_order` returns the module
with its `let` declarations permuted into that order, so every later stage
carries the fact by preserving list order rather than consulting a table.

Ordering happens in `compile_one_module` after the lint passes and before the
module is stored: lint reads the module as written, everything downstream reads
it in initialization order. New diagnostic `E4004`, defined beside the
module-granularity `E4003` import cycle it mirrors, spanning the first member's
name.

Scope decision (human): Lane's rule stays "top-level functions may forward
reference, top-level values may not". The resolver's ordered value scope is
untouched and `examples/invalid/02_top_level_let_forward_value.lane` still
reports E2001. That is consistent with dependency ordering rather than an
exception to it — in `let eager = read_later(3)`, the value names only an
earlier function and the function names a later value, so both references obey
the rule and only their composition needed an order.

Measured end to end through `lane run`, all three behaviors:
- the issue's reproduction prints `7` (was: `InternalRuntimeFailure(detail="Wasm instance-global lifecycle failure")`);
- a value cycle reports `error[E4004]: initialization cycle between \`a\`, \`b\`` with the offending declaration's span (was: reached the VM);
- a direct forward reference between values still reports `error[E2001]`.

Corpus: `examples/valid/90_initializer_reaches_later_value.lane` (runs, prints
`42`) and `examples/invalid/84_initialization_cycle.lane` (E4004), both wired
into `examples/fixtures/lane-run.json`. Compile-level regressions cover the
same four cases; red/green measured — the cycle test fails with the analysis
present but unwired.

Verified: `moon check --target native --warn-list +73` clean (0 warnings);
`moon test --target native` 1455/1455; examples gate exit 0 against the pinned
fixture; `.mbti` drift is the two new public analysis types.
