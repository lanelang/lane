# ISS-292: Confine selective CPS to the declarations it produces

## Description
`rewrite_cps_source_metadata` walks every type, data constructor, and value in
the registry up to the pre-CPS counts and rewrites each one unconditionally.

Effect specialization drops the terms of a definition it has copied but keeps
that definition's metadata. CPS therefore rewrites declarations that no longer
appear anywhere: it turns the types *under* them into companion form while
leaving the binders that scope them alone, and the result is a declaration whose
payloads mention `E%context` while its parameter list still says `E`.

`examples/valid/37_coroutine_scheduler.lane` is the measured case: 19
`UnknownTypeParameter` and 2 `TypeMismatch` after monadic-lift, all in
declarations of `Step[E]`, `Task[E]`, `Runnable[E]`, and a definition named
`run_step`, none of which the specialized program refers to.

Two shortcuts were tried during ISS-284 and both are wrong:

- Mapping a type's own parameters through `companion_parameter` makes the
  applied forms of those same dead types fail kind checking, trading 19
  diagnostics for 19 others.
- Mapping a data constructor's hidden parameters contradicts the erasure of
  effect-kind existentials that `modules/lanec/loisvm_lowering/lower_wbtest.mbt`
  pins by asserting a stored witness count of zero.

## Design
A dead declaration does not need to be rewritten; it needs to be left alone. The
program that reaches effect lowering is verified (ISS-284), so every declaration
in it is already legal Buslane. Legality is not the problem — CPS is making
these declarations *illegal* by half-rewriting them.

So separate two questions that are currently conflated:

- **Is a declaration legal Buslane?** Applies to everything in the registry, and
  is what `verify_program` asks.
- **Has a declaration been through this phase?** Applies only to what the phase
  produced, and is what `validate_mon_trans_output` asks.

CPS computes the closure of declarations reachable from `program.terms` — the
term list effect specialization already pruned — and rewrites only those.
`validate_mon_trans_output` is scoped to the same closure, because it currently
walks the whole registry and would reject exactly the declarations CPS is now
correctly leaving alone.

Rewriting per declaration rather than per table is not lazy. A top-level binding
may refer to a value defined by a later term, since `verify_terms` puts every
identity in scope before checking any of them, and a recursive group refers to
itself. Each round must therefore commit every declaration's target type before
lowering any body.

`rewrite_type` already computes that type without lowering anything, so this
does not wait on ISS-293. Scoping the walk is the whole change: the same
computation, over the closure instead of over the table.

`erase_residual_effects` also walks the whole registry, but it only empties
effect rows, which leaves an untouched declaration legal. It can stay as it is.

- [x] CPS rewrites only declarations reachable from the program it is given.
- [x] `validate_mon_trans_output` checks only those declarations, and the
      distinction between legality and phase completion is stated where the two

## Close Notes
`collect_program_declarations` walks a program's terms for the values and data
constructors it names, and both passes are scoped to that set. The comment where
each check lives says which question it asks, since that is what decides whether
a declaration is in scope for it.

Two things turned out smaller than the design expected:

- The types loop in `rewrite_cps_source_metadata` was a copy that changed
  nothing, so only values and data constructors are actually rewritten and only
  those needed scoping. `CpsSourceCounts::types` is gone with it.
- It does not depend on ISS-293. `rewrite_type` already computes a declaration's
  target type without lowering anything, so committing every declaration's type
  before lowering any body was never blocked.

Measured over `examples/valid`: the 19 `UnknownTypeParameter` after monadic-lift
are gone, and no program produces any. Both remaining failures are now two
`TypeMismatch` each.

`examples/valid/37_coroutine_scheduler.lane` is not yet clean. Its
`UnknownTypeParameter` diagnostics, which were this issue's subject, are
resolved; the two mismatches it still reports are the same kind
`45_async_effect.lane` reports, so they belong with ISS-293.

The regression observes `MonadicContinuationsLifted` directly. It rejects any
`UnknownTypeParameter`, requires the complete diagnostic set to contain exactly
two `TypeMismatch` values, and therefore keeps ISS-292's fix separate from the
known ISS-293 failure.

A unit test had to change with this: it lowered an expression against a program
whose terms did not contain it, which no longer rewrites anything. That the test
had to start reflecting the real pipeline is the rule working.
