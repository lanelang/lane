# ISS-286: Rewrite every reference when effect specialization copies a type

## Description
Effect specialization replaces an effect-generic data type with a monomorphic
copy but leaves some references pointing at the original, so the specialized
program does not typecheck.

`examples/valid/37_coroutine_scheduler.lane` reports four `TypeMismatch`
diagnostics on the effect-lowering input, three of the same shape and one
wrapping it:

```
expected = Apply(Constructor(Scheduler), [EffectArgument(Coroutine)])
actual   = Constructor(Scheduler%effect)
```

`Scheduler` is the source type with one effect parameter; `Scheduler%effect` is
the specialized copy with none. The expression was rewritten to the copy while
the type it is checked against still names the generic applied to its effect
argument.

The program runs correctly, because the two types have the same layout. Only the
type level disagrees.

This is also the sole remaining source of `UnknownTypeParameter` after ISS-285:
19 of them appear after monadic-lift for this one program, downstream of the
same mismatch.

## Design
Specialization must rewrite type references everywhere a specialized type can be
named, not only where the pass currently walks. Find the sites it misses by
verifying the specialized program and following the reported types back, rather
than by enumerating suspected cases.

Whether the fix belongs in the walk or in how a specialized copy is registered
should follow from what the missed sites have in common.

## Acceptance Criteria
- [ ] `examples/valid/37_coroutine_scheduler.lane` verifies after effect
      specialization.
- [ ] The `UnknownTypeParameter` diagnostics it produces after monadic-lift are
      gone.
- [ ] A regression test covers specializing a data type that appears in more
      than one reference position.
- [ ] `moon check`, `moon test --target native`, and
      `tools/check-lane-run-examples.sh` pass.
