# ISS-280: Bound Wasm control-flow nesting by program structure

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: area/wasm, area/loisvm-lowering, performance, codegen, agent
- Assignee: unassigned

## Description
CFG-to-Wasm restructuring emits a tower of nested `block`s whose depth grows with
the number of basic blocks in a function rather than with the program's actual
control-flow structure. `examples/valid/78_structural_derivation.lane` reaches
46 levels of nesting inside one function, and takes 58s to run through the
default Wasmoon tier, against 0.04s through the LoisVM interpreter on the same
bytecode.

The source that produces this is a straight-line sequence of statements with a
few `if`s and `match`es, nested at most two or three levels syntactically. At
the deepest point the generated module holds 45 nested `block`s and one `if` —
no loops, no exception regions. That is the shape produced by wrapping every
forward-branch target in its own `block` so `br N` can reach it.

Measurements. Compiling is not the problem; only the Wasm tier is:

| stage | time |
| --- | --- |
| `lane check` | 0.03s |
| `lane explore` (through Wasm generation, no execution) | 0.06s |
| `lane run --no-jit` (LoisVM interpreter) | 0.04s |
| `lane run` (Wasmoon) | 58s |

Module size does not explain it. `examples/valid/83_utf8_string_char_i32.lane`
emits a larger module and runs 24x faster:

| | 78 | 83 |
| --- | --- | --- |
| wasm text | 560KB | 786KB |
| functions | 145 | 253 |
| largest function | 3379 lines | 1378 lines |
| max nesting | 46 | 16 |
| Wasmoon | 58s | 2.4s |

Truncating example 78's entry body to its first N statements separates size from
depth. Size grows 2.6x while depth grows 4.2x and time grows 80x:

| statements | wasm | max nesting | time |
| ---: | ---: | ---: | ---: |
| 4 | 218K | 11 | 0.76s |
| 7 | 362K | 17 | 4.22s |
| 9 | 395K | 22 | 6.19s |
| 11 | 439K | 34 | 10.39s |
| 13 | 508K | 38 | 23.01s |
| 18 | 560K | 46 | 60.61s |

Structural derivation is not itself the cause: each `derive` use measured alone
costs 0.4-1.0s. The cost comes from many basic blocks living in one function.

## Design
Restructuring should produce nesting proportional to real loop and conditional
depth. Sibling forward-branch targets in a straight-line region should share one
enclosing level instead of each adding one, and a region with many targets
should fall back to the `loop` plus `br_table` dispatcher that ADR-0076 already
defines for irreducible CFGs, which the ADR explicitly permits selectively.

ADR-0076 says reducible CFGs are restructured into nested `block`, `loop`, and
`if` control but places no bound on depth. Whatever bound is chosen belongs in
that ADR.

Splitting large entry bodies into several functions would also cap depth, but
that changes lowering policy rather than fixing the restructurer, so treat it as
a fallback.

## Acceptance Criteria
- [ ] Nesting depth for `examples/valid/78_structural_derivation.lane` is
      proportional to its syntactic nesting rather than its basic-block count.
- [ ] That example runs through the default Wasm tier in a time comparable to
      other examples of similar module size.
- [ ] A regression check pins maximum nesting depth so it cannot silently grow.
- [ ] ADR-0076 states the depth bound.

## Notes
- 2026-07-31: Whether Wasmoon is superlinear in nesting depth is unproven; the
  evidence is correlational. Isolating it needs the actually emitted module
  bytes compiled by another engine, which ISS-281 blocks. The generated depth is
  wrong on its own terms regardless of where any engine's cliff sits, and fixing
  it is expected to remove the symptom either way.
- 2026-07-31: Settled once ISS-281 made the explored text a faithful module.
  `wasmtime compile` handles the same example 78 module in **0.06s**, against
  **58s** in Wasmoon; example 83 takes 0.02s. A production engine is untroubled
  by depth 46, so the runtime cost belongs to Wasmoon, not to the module.

  This re-scopes the issue. The 58s is a Wasmoon problem and should be filed and
  pursued there; nesting depth 46 for a straight-line body remains poor output
  worth bounding, but it is a code-quality concern rather than the cause of the
  observed slowdown, and its priority should drop accordingly.

  Since the cost is not in our code generation, the LoisVM interpreter running
  the same bytecode in 0.04s is the relevant comparison: the semantics were
  never expensive.
