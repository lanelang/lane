# ISS-319: Reject a wrong parenthesis arity in the grammar, not in an action

## Metadata
- Type: bug
- Status: closed
- Priority: 2
- Labels: area/buslane, correctness, public-api, agent
- Assignee: -
- Created: 2026-08-04
- Updated: 2026-08-04
- External ref: modules/buslane/text/parser.mbty, modules/buslane/text/imports.mbt

## Description
`parse_type_text` returns `Result`, and on some malformed input it aborted the
process instead. A parenthesized group of types is one production shared
between a function type's parameter list and a parenthesized type, because
the two cannot be told apart until the token after the closing parenthesis.
Only a group of exactly one type can be the second reading, and that arity was
checked in the semantic action, which had nowhere to report a failure and so
called `abort`.

The root is that a generated semantic action cannot raise: `yy_action_*`
carries no `raise` annotation, so an action that discovers bad input has only
the process to end.

## Reproduction
```moonbit
parse_type_text("(I64, Bool)")
```

Aborts with `a parenthesized Buslane type holds exactly one type`; the test
executable exits with signal 6. `parse_type_text("()")` does the same.

## Design
State the arity in the grammar, so the action never has to reject one. A group
splits into `paren_type`, which holds exactly one type, and `paren_types`,
which holds none or two or more; a parameter list accepts either and a
parenthesized type accepts only the first. The split is decided by the token
after the first type — `)` or `,` — so it stays LALR(1) and adds no conflict.

Superseded alternatives: giving the action a channel to report through, which
either infects every type-valued nonterminal with `Result` or needs a mutable
cell read after the parse; and a post-parse validation pass, which cannot see
an arity the AST no longer records.

## Acceptance Criteria
- [x] `parse_type_text` returns `Err` on every parenthesis arity it rejects.
- [x] Every accepted type is unchanged, including a parameter list of zero, one, and many.
- [x] The grammar reports no new conflicts.
- [x] No semantic action in the package can fail on well-formed lexer output.

## Close Notes
`parenthesized_type` is deleted. `atom_type` takes `paren_type` directly and a
parameter list takes `parameter_types`, which is `paren_type` or `paren_types`.
`(I64, Bool)` and `()` are now parse errors, `(I64)` is still a parenthesized
type, and `()`, `(I64)`, `(I64, Bool)` before an arrow are still parameter
lists of zero, one, and two.

The two other aborts reachable from this grammar were checked and are not
defects of the same kind:

- `validated_literal` in `modules/buslane/text/literal.mbt` runs after
  `validate_literal_tokens` has already rejected every bad literal at the token
  level, and the type grammar contains no literal at all, so `parse_type_text`
  cannot reach it. It stays an assertion, though it is an assertion that holds
  only because a token-level pass and the grammar agree about which `INT` is a
  literal — the two enumerations match today.
- `extend_owner_type_name` in `modules/lanec/parser/yacc_parser/imports.mbt` is
  unreachable by construction: `owner_path_expression` has two productions, one
  producing `Name` and one calling this function, which maps `Name` to
  `QualifiedName` and `QualifiedName` to itself, so the owner is always one of
  those two by induction.

Verified: `moon check --target native --warn-list +73` clean (0 warnings);
`moon test --target native` 1474/1474; examples gate exit 0 against the pinned
fixture; the generator still reports exactly one shift-reduce conflict, the
same count as before the change.

Follow-up ISS-330 located that independent conflict in adjacent match
alternatives and removed it with an explicit canonical terminator. Parser
generation now reports zero conflicts.
