# ISS-289: Report an unusable core-optimizer input instead of aborting

## Description
`expression_has_empty_effect` aborts the process when the facts query cannot
synthesize an expression:

```moonbit
Err(_) => abort("core optimizer requires a verified Buslane expression")
```

The user sees a crash with no file, no expression, and no reason. The reason is
discarded before the message is built, so even a developer has to patch the
compiler to learn what failed — which is what this issue was found by doing.

The path is reachable. Effect lowering is not yet verified on its output
(ISS-284), so the optimizer can be handed a program that does not typecheck, and
this is where it notices.

## Design
Threading a failure out was considered and rejected. `expression_has_empty_effect`
is called from the middle of a recursive simplifier, and the question it answers
already has a safe unknown: the optimizer only uses it to decide whether removing
a computation is sound, so an expression it cannot synthesize should be treated
as performing something and left alone.

## Close Notes
An expression the facts query cannot synthesize is now treated as effectful, so
the optimizer leaves it alone instead of aborting the compilation. That is the
answer the optimizer's own question already had a safe default for.

Reporting the underlying failure belongs one level up, where ISS-284 will verify
the program the optimizer is handed. A defect will be a diagnostic naming the
stage that produced it, rather than a crash inside a pass that merely noticed.
