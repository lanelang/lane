## Description
Storing a callable as a generic value currently canonicalizes its internal
calling convention, rather than merely storing its handle. `erase_value` calls
`canonical_callable_type` and `make_callable_adapter` before `EraseI64`;
`unerase_value` performs the reverse adaptation. In `type_adaptation.mbt`,
`canonical_callable_value_type` turns concrete non-Unit callable parameters and
results into erased values, except for already-bound erased parameters.

In the ISS-434 Basic baseline, Core through Runtime ANF stores the original 18
test callables in a List. Physical emission inserts wrappers. Reading the List
and executing a test produces this actual path (IDs are baseline observations,
not stable contracts):

```text
execute_tests -> adapter f240 -> adapter f317 -> original test

f240: erase_i32(context); erase_i64(continuation); call canonical callable
f317: unerase_i32(context); unerase_i64(continuation); call original callable
```

The List legitimately selects among different source functions. The two
opposite ABI adaptations are introduced by representation, not source-level
dispatch. The entry alone materializes 18 environments and 18 closures; their
construction and erasure expand to 378 of its 833 Wasm instructions. Shared
adapter function bodies do not eliminate these allocations or call layers.

## Design
Review the boundary between opaque callable storage and invocation under a
generic contract. Determine whether the existing representation can preserve
the original complete callable contract through storage, or whether a proven
inverse-adaptation elimination is required. Confirm the representation decision
with the user before implementation; this issue does not preselect a new ABI.

Whichever approach is chosen, one owner must derive the storage/call contract.
Producer and consumer must change together. Preserve higher-kinded and effect
companion witnesses, ownership, recursive contracts, and generic fallback.
Do not simply omit an adapter at one end, assume equal slot widths imply ABI
equivalence, or add another emission-time specialization policy.

## Acceptance Criteria
- [ ] Document the agreed storage versus invocation contract and its owner.
- [ ] A regression covering callable insertion, forwarding through a generic
      container, extraction, and invocation proves equivalent behavior and the
      absence of the demonstrated inverse adapter chain.
- [ ] Cover multiple possible callees, nested higher-order parameters,
      polymorphic answer/residual parameters, and a genuinely necessary ABI
      adaptation that must remain valid.
- [ ] Use public behavior/Explore tests where possible; any private tests
      inspect contracts structurally, without fixed function IDs or ordering.
- [ ] Record real Basic adapter bodies, environment/closure sites, erase/unerase
      operations, call paths, Wasm size, and suite correctness before/after.
