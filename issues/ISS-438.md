# ISS-438: Avoid rematerializing closure environments with static captures

## Description
Canonical adapter implementations are shared, and `make_callable_adapter`
already defers adaptation. However, when `materialize_callable_adapter` is
required, it emits an environment and closure for that use. Implementation
identity sharing does not imply closure-value sharing.

In the ISS-434 baseline there are 597 MakeEnv and 567 MakeClosure sites. A scan
of initial VM CFG finds 120 environment constructions whose sole capture is a
locally defined ConstFunction, including the 18 test entry wrappers. These are
static-capture candidates, not proof that all 120 allocations can be removed.
Repeated allocation/header/capture initialization contributes to caller size
even when the adapter body itself exists only once.

## Design
After the adaptation cleanup in ISS-435, identify remaining static-capture
environments using producer-owned value facts. Determine the smallest sound representation
under the existing static-image and callable ownership contracts. Confirm any
new lifetime or identity policy with the user before changing it.

Preserve full callable ABI, environment layout, valid table references, and
retain/release behavior. Captured dynamic witnesses or runtime values must not
be mistaken for static data. Do not create another function-dedup mechanism or
special-case the Basic test list. Do not assume this issue also authorizes
arbitrary static evaluation of source aggregate initialization.

## Acceptance Criteria
- [ ] Record remaining candidates after ISS-435 and explain which captures and
      lifetime contracts make them eligible or ineligible.
- [ ] Eligible repeated constructions reuse a valid static/no-allocation
      representation, with no duplicate semantic identity producer.
- [ ] Test repeated creation, invocation, storage, and release through public
      behavior and structural allocation observations.
- [ ] Dynamic captures/witnesses remain correctly represented and owned.
- [ ] Record Basic environment/closure counts, code and data bytes, and runtime
      correctness; report any code-to-data tradeoff explicitly.
