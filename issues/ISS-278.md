## Description
The same prefix `-` was handled by three stages under three different models.

The grammar already split: in pattern position `"-" INT` produced one
`IntegerLiteral("-" + $2)`, so `Pattern` had no unary node at all, while in
expression position `"-" unary_expression` produced `Unary(operator=Neg, ..)`.

Name resolution then mapped `Neg` to `op_neg` unconditionally and resolved it as
a value reference, without looking at the operand.

Type checking then recognized `Unary(Neg, Literal(Integer))` against `I32` and
`I64` expectations, discarded the resolved `op_neg` reference, and rebuilt a
single literal from the sign and the digits. That is the pattern-position
grammar rule, re-implemented one stage later and once per numeric width.

Three consequences followed directly from the split:

- `-42 : I64` required `op_neg` to be in scope even though no call survived.
- Each signed width needed its own checking arm and its own
  `check_negated_*_literal`.
- The spec disagreed with itself about the mode: `language-spec.typ:1199` places
  the merge in `Int` introduction, which reads as synthesis, while `:2444` calls
  it the counterpart of the `S32` checking rule `A-S32NegatedLiteralCheck`.
  A checker-side merge has to pick one; a parser-side fold makes the question
  disappear.

Floating literals had the same asymmetry, unnoticed because `F64` has no
boundary value that is unwritable.

## Design
Fold the sign in the grammar action for prefix `-`, not in the grammar shape and
not in the checker.

`negated_expression` returns `IntegerLiteral("-" + raw)` or
`FloatingLiteral("-" + raw)` when the operand is an unsigned numeric literal,
and `Unary(operator=Neg, ..)` otherwise. An already-signed literal is not folded
again, so `- -1` stays an operator application.

Adding `"-" INT` and `"-" DOUBLE` as grammar rules was tried first and rejected:
the baseline grammar has zero conflicts, and those rules introduce 64
reduce conflicts resolved silently by presentation order. LR(1) cannot see that
the sign is lexically adjacent to a literal token, so the fact belongs in the
action, where the grammar stays unambiguous.

After the fold, no `Unary` node ever wraps a bare numeric literal, so both later
stages lose their knowledge of the case entirely: resolution never looks up
`op_neg` for a literal, and `check_i32_literal` / `check_i64_literal` already
accept signed spellings, since `is_decimal_integer_literal` strips a leading
`-` and `parse_int64` represents both signed minimums.

## Notes
- 2026-07-31: Supersedes the checking-mode implementation from ISS-277. That
  fix was correct for the reported symptom but added a second copy of a rule
  that should not have been in the checker at all.
- 2026-07-31: Pattern position still folds in the grammar, where no ambiguity
  exists. Patterns accept `"-" INT` but not `"-" DOUBLE`; expressions now accept
  both. Making pattern floats symmetric would widen the accepted language and
  was left alone.

## Close Notes
Replaced the action of the prefix `-` rule in
`modules/lanec/parser/yacc_parser/parser.mbty` with a call to
`negated_expression`, added that helper and `is_signed_literal` beside the other
grammar-action helpers in the same package, and regenerated
`generated_parser.mbt`. The generated diff is the single action body; the
grammar shape is untouched and still reports no conflicts.

Deleted both negation arms from
`modules/lanec/typecheck/checked_expression.mbt` and both
`check_negated_*_literal` functions from `modules/lanec/typecheck/literal.mbt`.
Net effect on the checker is removal only.

Dropped the now-unused `op_neg` declarations from the `I32` and `I64` fixtures
in `modules/lanec/compile/i32_wbtest.mbt`,
`modules/lanec/typecheck/i32_wbtest.mbt`, and
`modules/lanec/typecheck/i64_wbtest.mbt`. The lowering snapshot in the compile
fixture did not change, confirming the call was already being discarded.

Verification:
- `moon check --warn-list +73` and `moon check modules/lanec --target all
  --deny-warn` clean.
- `moon test --target native`: 1335 tests, all passed, no snapshot updates.
- `tools/check-lane-run-examples.sh` passes against a Basic library without the
  redundant `import Basic.Ops.{ op_neg }` lines.
- Manual: a module with no imports at all accepts `-9223372036854775808`,
  `-2147483648`, `-42`, and `-1.5`; `- -1` and `-value` still resolve `op_neg`;
  `-9223372036854775808` now also checks in synthesis position, inside a match
  scrutinee.

Downstream: the Basic library's `Basic.Data.I64` and `Basic.Data.I32` no longer
need `import Basic.Ops.{ op_neg }`, and the compiler reports those imports as
unused. Removing the two lines is required for the example smoke fixtures to
pass against that library.
