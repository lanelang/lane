## Description
Originally filed as "five examples fail on a Basic parse error". Follow-up
measurement disproved that premise: the failure was transient. The gate
compiles examples against the LIVE working tree of the sibling Basic checkout,
and the run happened to catch `src/data/string.lane` mid-edit (a half-typed
signature rendered as `: I64` at 68:4; the parser expected a parameter start —
identifier, `offer`, `auto`). Basic's committed HEAD and its finished working
tree both parse; rerunning the gate afterwards exits 0 with all examples
passing.

Grammar confirmation that no parser work is owed: the surface grammar defines
`parameter : parameter_modifiers identifier ":" type`
(modules/lanec/parser/yacc_parser/parser.mbty:424), so the language has no
anonymous-parameter form and a bare `: I64` at parameter start is ill-formed
by definition. The expectation set in the diagnostic is exactly the legal
parameter starts, so the parser and its message were both correct.

The remaining question is a design decision, not a bug: a gate that reads
another repository's uncommitted state is not reproducible — any keystroke in
Basic can turn this repo's gate red, and two runs minutes apart can disagree
(both happened during ISS-307 verification). That may be acceptable, even
intended, as live cross-repo integration signal for a human co-developing
both; it is misleading for agents treating the gate as a prerequisite.

## Design
Human decision required. Options, not mutually exclusive:
- Pin the gate to a recorded Basic revision (worktree checkout), refreshed
  deliberately; full reproducibility, loses live signal.
- Keep the live tree but have the runner print the Basic commit plus a dirty
  marker in its report, so a red gate is attributable at a glance.
- Status quo, documented: agents treat Basic-side parse failures as
  environmental, retry once, and never file them as compiler findings.
Agents do not modify the Basic repository either way.

## Acceptance Criteria
- [x] The chosen policy is recorded (in the runner or its docs) and the runner's output makes a Basic-side failure attributable to Basic state.
- [x] The gate runs only when Basic is initialized at the exact gitlink revision with a clean worktree.
- [x] Missing, mismatched, and dirty fixtures fail before the Lane build without modifying Basic.

## Close Notes
Decision (human): pin Basic as a git submodule, GHC boot-library style. The
examples fixture is no longer the user-facing `$LANE_HOME/basic` installation
— that path is a runtime contract for users, and doubling it as a test
fixture is what let the gate race a live editor.

Implementation: `basic` submodule at the repo root, pinned to Basic main
(`9084321887c1`). `.gitmodules` records the portable relative URL
`../basic.git` (resolves to the lanelang sibling repository for remote
clones); this machine's `.git/config` overrides the fetch URL to the local
sibling checkout so unpushed Basic commits stay reachable.
`tools/check-lane-run-examples.sh` now requires the submodule to be initialized,
checked out at the exact gitlink revision, and clean before it builds Lane. A
missing, mismatched, or dirty fixture fails immediately and tells the caller to
save any work before running `git submodule update --init --checkout basic`;
the gate never modifies Basic itself. It exports `LANE_HOME=$repo_root` only
after those checks, so the runtime resolves the verified submodule. The runner
mbtx and the user-facing `LANE_HOME` contract are untouched; `moon test` never
read the ambient variable because tests inject it as a parameter.

Moving the pin is an ordinary reviewed change: advance the submodule and
commit the new gitlink, ideally in the same lane commit that lands whatever
the newer Basic needs. Operational note: a gitlink referencing an unpushed
Basic commit is unresolvable for remote clones — push Basic alongside lane.

Verified: `sh tools/check-lane-run-examples.sh` exits 0 against the pinned
fixture and prints `basic fixture: 9084321887c1`; live edits in `../basic`
are outside the gate's read path by construction.
