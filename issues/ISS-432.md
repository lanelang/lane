# ISS-432: Establish the dependency boundary for Lane-authored builds

## Description
The intended repository workflow is:

```text
lane run build.lane:build
lane exec basic.wasm:test
```

The first command should run an ordinary Lane build program that produces a
reusable linked WebAssembly module. The second command should execute an
exported entry without recompiling the source graph.

`lane compile` compiles one source module against explicit module interfaces,
and `lane link` consumes explicit object files. `lane inspect` now exposes the
compiler-owned projection of one source file's module identity and direct
imports, while Lane Runtime V1 exposes structured command input and output.
Basic still lacks the structured source-discovery API and build-graph
implementation needed to compose these primitives into the complete workflow.
Reimplementing Lane import parsing in Basic would create a second producer of
module facts, while moving whole-graph scheduling into a `lane compile-graph`
command would move build policy into the compiler.

An experimental static source manifest also exposed a separate compiler
performance defect: consuming a long known `List` recursively can cause large
compile-time expansion before the build program executes. That defect must be
fixed independently; it is not a reason to move graph ownership into the
compiler.

## Design
Keep the existing compilation boundary and assign each fact one owner:

- The Lane parser/module-input boundary owns the source module identity,
  direct imports, and source fingerprint for one source unit.
- Basic.Build owns repository discovery, the aggregate dependency DAG,
  topological scheduling, caching, parallelism, output paths, and the final
  explicit object set passed to `lane link`.
- `lane compile` remains a single-module operation over explicit source and
  interface inputs.
- `lane link` remains an explicit operation over object inputs and export
  requests.

Expose a stable, structured dependency projection that Basic.Build can consume
without parsing Lane source syntax. Separately provide the structured file and
process facilities needed to discover sources and invoke compiler commands.
ADR-0144 owns this boundary and its public projection.

Do not introduce:

- a compiler-owned `compile-graph` scheduler;
- an ad hoc newline-delimited `object-list` protocol;
- shell `find`, `ls`, or glob parsing as the build model; or
- duplicated module/import interpretation in Basic.

## Acceptance Criteria
- [x] An ADR assigns single ownership for direct source dependencies, the
      aggregate build graph, scheduling, cache policy, and link inputs.
- [x] The compiler exposes stable structured direct-dependency facts without
      performing repository discovery or graph scheduling.
- [x] Basic has structured source discovery and command-result facilities, or
      an equally explicit manifest mechanism, without shell-output parsing.
- [x] Basic.Build constructs the dependency DAG and invokes the existing
      single-module compile and explicit-object link operations.
- [x] A black-box example builds a reusable WebAssembly module with
      `lane run build.lane:build` and then runs an exported test entry with
      `lane exec basic.wasm:test` without a nested `lane run`.
- [x] No build source duplicates Lane module/import facts, and no
      `compile-graph` or `object-list` fallback is introduced.
- [x] The long-known-list compiler performance defect is tracked and verified
      independently from this build-system boundary by ISS-433.

## Notes
- 2026-09-02: A `compile-graph` command and newline-delimited object-list
  experiment were rejected and fully reverted because they combined compiler
  semantics, build policy, and an incidental transport format.
- 2026-09-02: ADR-0144 assigned the dependency boundary. `lane inspect` now
  projects one source file's parser-owned module and direct imports as stable
  JSON. Lane Runtime V1 command execution now accepts byte stdin and returns
  captured byte stdout and stderr. Structured source discovery in Basic and the
  end-to-end Basic.Build example remain open.
- 2026-09-03: Basic.Build now consumes an explicit source-path manifest, uses
  `lane inspect` for module facts, schedules the resulting dependency DAG, and
  passes explicit interface and object artifacts to the existing compile/link
  commands. End-to-end validation builds `basic.wasm` and executes its `test`
  export without recompiling the source graph.
- 2026-09-03: Self-hosting exposed duplicate direct-import facts when one source
  contained multiple import declarations for the same module. The canonical
  module-input projection now preserves the first declaration and emits each
  module once; Basic.Build does not compensate for compiler-owned facts.

## Close Notes

Closed after the public two-command workflow completed successfully against the
repository Basic sources. The build policy is ordinary Basic code; parser-owned
module facts, single-module compilation, and explicit-object linking remain at
their existing compiler boundaries.
