# ISS-277: Accept the I64 signed minimum as a negated literal

- Type: bug
- Status: closed
- Priority: 1

- Assignee: unassigned
- Created: 2026-07-31

## Description
`-9223372036854775808` could not be written in expression position, so the
`I64` minimum was not definable in Lane source. The `I32` counterpart
`-2147483648` worked.

`checked_expression.mbt` had one merged "negation plus immediately nested
integer literal" arm, guarded on `expectation.type_ == Primitive(I32)`, calling
`check_negated_i32_literal`. There was no `I64` arm and no
`check_negated_i64_literal`. Negated `I64` literals therefore fell through to
the generic `Unary` arm, which desugars to an ordinary `op_neg(N)` call and
requires `N` itself to be a valid `I64`. `9223372036854775808` is not, so the
minimum could never be written.

This was unimplemented spec, not a design tradeoff. `language-spec.typ:1199`
states the `Int` rule and names `-9223372036854775808` as acceptable;
`:2436` gives `A-S32NegatedLiteralCheck` for `S32`; `:2444` then requires the
corresponding signed-64-bit special case for an immediately negated `Int`
literal.

Observed downstream: the Basic library defines
`pub let minimum : I64 = i64_neg(2147483648)` in
`basic/src/data/i64.lane:8`, which evaluates to the `I32` minimum rather than
the `I64` minimum. That workaround exists because the correct literal could not
be written, and it is wrong by a factor of 2^32.

## Design
Add `check_negated_i64_literal` alongside `check_negated_i32_literal` and give
the checking match an `I64` arm mirroring the existing `I32` arm.

The magnitude is parsed on its own with `parse_uint64`, because
`9223372036854775808` does not fit in `Int64`. Magnitudes above `2^63` are
rejected, `2^63` yields the minimum, and anything smaller is negated normally.

Non-goals: no change to synthesis-mode negation, and no change to pattern
positions, which already accept the negated minimum through their own path.

## Notes
- 2026-07-31: Resolution still requires `op_neg` to be visible for any unary
  minus, even one the checker later merges into a literal. That matches the
  existing `I32` behavior and is why both new examples import `Basic.Ops.*`.
  Whether the merge should happen before name resolution is a separate spec
  question and was not changed here.
- 2026-07-31: Checking-mode only. `language-spec.typ:1199` places the merge in
  the `Int` introduction prose, which reads as synthesis, while `:2444` says
  "the corresponding" special case to the `S32` checking rule. Extending the
  merge to synthesis would change lowering for every negated integer literal in
  the language, so it is left for a separate decision.

## Close Notes
Added `SemanticChecker::check_negated_i64_literal` in
`modules/lanec/typecheck/literal.mbt` and a matching `Primitive(I64)` arm in
`modules/lanec/typecheck/checked_expression.mbt`, next to the existing `I32`
arm and sharing a comment that states why negation merges with its operand.

Verification:
- `moon check --warn-list +73` and `moon check modules/lanec --target all
  --deny-warn` clean.
- `moon test --target native`: 1335 tests, all passed.
- `tools/check-lane-run-examples.sh` passes.
- New tests: `modules/lanec/typecheck/i64_wbtest.mbt`, covering the accepted
  range with a pattern match on the minimum, the below-range literal, and the
  unnegated above-range literal.
- New examples: `examples/valid/85_i64_signed_minimum.lane` and
  `examples/invalid/81_i64_literal_underflow.lane`, both registered in
  `examples/fixtures/lane-run.json`.
- Runtime evidence: the example asserts `signed_minimum + signed_maximum == -1`,
  which holds only for -2^63; the pre-fix binary rejects the same source with
  `E3010`.

Follow-up not done here: `basic/src/data/i64.lane:8` still holds the wrong
`minimum`. It lives in the separate Basic repository and can now be written
correctly as `-9223372036854775808`.

Superseded by ISS-278. The checking arms added here were removed in favour of
folding the sign into the literal at parse time, which deletes the case from the
checker entirely instead of adding one arm per numeric width.
