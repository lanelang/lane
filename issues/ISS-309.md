# ISS-309: Verify binder declarations at their binding sites

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: area/buslane, correctness, verifier, agent
- Assignee: -
- Created: 2026-08-03
- Updated: 2026-08-03
- External ref: modules/buslane/verify.mbt

## Description
The verifier checks closed-kind value types (Function/Value/External) against
an empty scope during the metadata pass (`has_closed_metadata_type`,
verify.mbt:308), but binder-kind values (Parameter/Local/MatchBinder) are never
checked anywhere: `synthesize_function` (verify.mbt:490) reads each parameter's
declared type straight into the synthesized function type without verifying it
is well-formed in the enclosing type scope — while the result type on the very
next line IS verified (verify.mbt:506). The asymmetry admits garbage. Measured:
a Local binding whose declared type and whose function-literal parameter both
mention `TypeParameterId 9999` — an id that does not exist in the registry —
verifies with zero diagnostics, because equality compares free parameters by id
and nothing ever asks whether the id is real or in scope.

Binder sites also ignore ValueKind: a function literal may bind a value whose
kind is External (or Function, or Value) as its parameter; match and handler
binders are equally unchecked. ValueKind is load-bearing downstream — ISS-285
was precisely a lowering decision keyed on Function vs Local — so metadata that
lies about kinds passes the gate and misleads every consumer.

## Reproduction
```moonbit
let bogus : TypeParameterId = { index: 9999 }
let p = metadata.define_value("p", Parameter, Parameter(bogus))
let local_f = metadata.define_value("f", Local, Function([Parameter(bogus)], Primitive(Unit), Empty))
// Let(main, Let(local_f, fn(p) -> Unit { () }, ())) verifies clean.

let q = metadata.define_value("q", External, Primitive(I64))
// fn(q) -> I64 { q } with an External binder also verifies clean.
```

## Design
One uniform rule: every binding site verifies its binder's declared type in the
scope where the binder is introduced, and requires the binder-appropriate
ValueKind — Parameter for function-literal parameters, Local for let/letrec
locals (top-level lets keep their closed kinds), MatchBinder for match, payload,
result, and resume binders. This subsumes the current result-type-only check in
`synthesize_function` rather than adding a second mechanism next to it.

## Acceptance Criteria
- [x] Both reproductions above produce diagnostics (unknown/out-of-scope parameter; wrong binder kind).
- [x] Function parameters, let/letrec binders, match binders, handler payload/result/resume binders all verify type well-formedness in the correct scope.
- [x] Existing corpus (examples/valid, 1425 native tests) stays green.

## Close Notes
One rule, one owner: `VerifyContext::verify_binder` resolves the value,
requires a binder kind, and verifies the declared type in the scope the binder
is introduced into. Every binding site goes through it — function-literal
parameters, let and letrec binders, the match binder, data-alternative value
binders, default/literal alternative binders, handler result, payload, and
resume binders — replacing the ad-hoc `value_info` lookups that skipped both
checks. It subsumes `synthesize_function`'s result-type-only check rather than
sitting beside it. New diagnostic `InvalidBinderKind(value~, actual~)`;
`require_value` became dead and was deleted.

The kind rule is NOT "one exact kind per site", as this issue proposed. That
version was implemented first and measured: it fails, because lowering
rewrites binding constructs without reissuing ids. Two independent instances,
both found by running the suite against the strict rule —
`handler_elaboration.mbt:111` turns a clause's payload and resume binders into
a `FunctionExpr`'s parameters (MatchBinder would have to become Parameter),
and `cps/install.mbt:259` rebinds the resume binder with a `Let` (Parameter
would have to become Local). A rule demanding an exact kind makes those values
illegal at one end of a rewrite that is otherwise correct, so ValueKind cannot
be read as a property of the value; it records which construct binds it.

The enforced rule is therefore the exact complement of the metadata pass:
`ValueKind::is_term_binder` = `!has_closed_metadata_type`, so every value's
declared type is verified exactly once — closed kinds (Function/Value/External)
during the metadata pass against the empty scope, binder kinds
(Parameter/Local/MatchBinder) at the site that introduces them. Top-level
`Let`/`LetRec` bindings keep the closed kinds, as this issue asked. Both of
this issue's reproductions are still caught: the bogus-parameter one by the
type check (measured: pre-fix the same program yields zero
`UnknownTypeParameter`), the External-binder one by the kind check.

Fixture corrections the new gate exposed, all genuine metadata errors in
tests rather than rule relaxations: five top-level bindings declared `Local`
(elaborate_test, globals_test ×3, linked_program_test), one top-level letrec
declared `Local` (abi_wbtest), and handler binders declared `Local`/`Parameter`
where the construct binds them (buslane_test ×4, type_normalization_test,
README.mbt.md). One extended-verifier snapshot now records four copies of an
out-of-scope parameter instead of one — the annotation's binder type is
genuinely checked now; deduplication waits for ISS-311's provenance.

Regressions: both reproductions, the top-level-kind rule, and a test pinning
that one id verifies both as a match binder and as a function parameter — the
interchangeability the rewrite instances above depend on.

Verified: `moon check --target native --warn-list +73` at baseline (9
warnings, none in buslane); `moon test --target native` 1447/1447; examples
gate exit 0 against the pinned fixture; `.mbti` drift is exactly the new
diagnostic case.
