# ISS-432: Establish the dependency boundary for Lane-authored builds

## Description
The intended repository workflow is:

```text
lane run build.lane:build
lane exec basic.wasm:test
```

The first command should run an ordinary Lane build program that produces a
reusable linked WebAssembly module. The second command should execute an
exported entry without recompiling the source graph.

The current public primitives do not yet let such a build program own this
workflow cleanly. `lane compile` compiles one source module against explicit
module interfaces, and `lane link` consumes explicit object files, but Basic
does not have a structured source-discovery API or a compiler-owned projection
of each source file's direct module dependencies. Reimplementing Lane import
parsing in Basic would create a second producer of module facts, while moving
whole-graph scheduling into a `lane compile-graph` command would move build
policy into the compiler.

An experimental static source manifest also exposed a separate compiler
performance defect: consuming a long known `List` recursively can cause large
compile-time expansion before the build program executes. That defect must be
fixed independently; it is not a reason to move graph ownership into the
compiler.

## Design
Keep the existing compilation boundary and assign each fact one owner:

- The Lane parser/module-input boundary owns the source module identity,
  direct imports, and source fingerprint for one source unit.
- Basic.Build owns repository discovery, the aggregate dependency DAG,
  topological scheduling, caching, parallelism, output paths, and the final
  explicit object set passed to `lane link`.
- `lane compile` remains a single-module operation over explicit source and
  interface inputs.
- `lane link` remains an explicit operation over object inputs and export
  requests.

Expose a stable, structured dependency projection that Basic.Build can consume
without parsing Lane source syntax. Separately provide the structured file and
process facilities needed to discover sources and invoke compiler commands.
The exact wire/API shape requires an ADR before implementation.

Do not introduce:

- a compiler-owned `compile-graph` scheduler;
- an ad hoc newline-delimited `object-list` protocol;
- shell `find`, `ls`, or glob parsing as the build model; or
- duplicated module/import interpretation in Basic.

## Acceptance Criteria
- [ ] An ADR assigns single ownership for direct source dependencies, the
      aggregate build graph, scheduling, cache policy, and link inputs.
- [ ] The compiler exposes stable structured direct-dependency facts without
      performing repository discovery or graph scheduling.
- [ ] Basic has structured source discovery and command-result facilities, or
      an equally explicit manifest mechanism, without shell-output parsing.
- [ ] Basic.Build constructs the dependency DAG and invokes the existing
      single-module compile and explicit-object link operations.
- [ ] A black-box example builds a reusable WebAssembly module with
      `lane run build.lane:build` and then runs an exported test entry with
      `lane exec basic.wasm:test` without a nested `lane run`.
- [ ] No build source duplicates Lane module/import facts, and no
      `compile-graph` or `object-list` fallback is introduced.
- [x] The long-known-list compiler performance defect is tracked and verified
      independently from this build-system boundary by ISS-433.
