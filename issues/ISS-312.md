## Description
Buslane now has four type/effect compatibility relations, and their asymmetries
are principled but unwritten:

- `types_definitionally_equal` — same denotation (alpha after normalize).
- `type_is_consumable_as` — value fits a position; widens latent effects by
  residual terms only; contravariant parameters. Documented in code.
- `function_implementation_matches` (verify_function_implementation.mbt:36) —
  implementation conforms to its own declaration: parameters invariant, effect
  widening by plain subset, algebraic terms included. No doc comment, no
  glossary term, and no written reason why algebraic widening is legal here but
  forbidden at argument positions (the reason: a declaration owns its ABI and
  the definition is lowered under it, while an argument's value already has a
  fixed ABI — a `let f : () -> Unit ! {A} = fn() {...}` verifies where the same
  binding via `Ref(pure_g)` is rejected, and nothing explains that difference).
- `effect_is_subeffect_of` — public plain-subset relation; callers must choose
  between it and consumability's stricter rule with no guidance.

CONTEXT.md also uses three bold glossary references it never defines:
**Metadata Registry**, **Effect Flavor**, **Buslane Type Logic** (the last
appears only in a Relationships bullet). Per the review standard, the glossary
is law; a term used in bold must have a definition.

## Design
Add glossary entries for the three missing terms and one entry per relation
stating its question, direction, and widening rule; give
`function_implementation_matches` a doc comment carrying the declaration-owns-
the-ABI rationale. No behavior changes.

## Acceptance Criteria

- [x] Each of the four relations has a glossary entry naming its question and its widening rule.
- [x] `function_implementation_matches` documents why its rules differ from consumability.

## Close Notes
Defined the three missing owner terms and named the four compatibility
relations by the question each answers. The glossary now distinguishes
definitional equality, value consumability, direct function implementation
conformance, and plain effect subsetting, including their direction and exact
widening policy.

Documented the ABI-ownership reason for implementation conformance to admit
algebraic effect widening while function-value consumability does not. The
public subeffect API now directs callers to consumability when they are checking
a callable value rather than a declaration-owned implementation.
