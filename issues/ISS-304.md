## Description
After the planned transformation is behaviorally stable, move effect
specialization out of the executable orchestration package. The current family
of `effect_specialization_*` files is a coherent compiler phase and a repeated
filename prefix inside an unrelated package.

## Design
Create `modules/lanec/effect_specialization` with a small public `specialize`
entrypoint and an owner-local error type. The package may depend on Buslane and
focused analysis packages but must not depend on `lanec/executable`.
`executable` remains responsible only for pipeline orchestration and error
adaptation.

## Acceptance Criteria
- [x] The new package owns planning, allocation, rewriting, and their tests.
- [x] Its public interface exposes only the phase entrypoint and error contract needed by executable elaboration.
- [x] `lanec/executable` contains no specialization implementation files.
- [x] No dependency cycle or accidental public API expansion is introduced.
- [x] Generated `.mbti` changes are reviewed.

## Close Notes

Created `modules/lanec/effect_specialization` as the owner of planning,
allocation, rewriting, errors, and white-box tests. Its generated interface
contains only `specialize` and `SpecializationError`. The executable package
adapts that owner-local error to its existing
`UnsupportedEffectSpecialization(detail)` boundary, so upstream public API is
unchanged. The monadic-lift integration test remains beside executable
orchestration.
