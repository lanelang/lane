## Description
`verify_terms` reports an unbound callable dependency — an eager top-level
initializer reaching a later binding through a callable — as
`UnknownValue(dependency)` (verify.mbt:603). Direct references to later
top-level bindings follow the same path through `ValueScope::contains`. These
values are not unknown: they resolve in metadata and are legal to reference
from a deferred function body; the defect is that they are not initialized at
the eager evaluation point. Reusing `UnknownValue` misstates the rule that
fired, the same category-error pattern ISS-314 removed from the kind checks
(`ExpectedEffectArgument` vs a fabricated `KindMismatch`).

Found during the re-check of the buslane review: probe programs for the eager
call, indirect call, and stored-closure shapes all fail with a diagnostic that
reads as a scoping error rather than an ordering error.

## Design
Model value availability explicitly as `Available | Deferred | Absent` rather
than reducing both unavailable states to `ValueScope::contains == false`.
`Deferred` means a known later top-level binding and produces a dedicated
initialization-order diagnostic carrying both the eager initializer and the
dependency. `Absent` continues to produce `UnknownValue`.

The fixed-point callable analysis returns a named domain record rather than a
tuple, and reports the same dedicated diagnostic. Direct and transitive paths
therefore share one semantic rule without moving diagnostic policy into the
dependency collector. Rendering exposes the initializer/dependency edge; the
existing provenance anchor continues to identify the term being verified.

## Acceptance Criteria
- [x] Direct references to deferred top-level bindings report a dedicated kind carrying initializer and dependency.
- [x] Callable and transitive callable dependencies report the same dedicated kind.
- [x] `UnknownValue` is reported only for identities that do not resolve or are outside both the available and deferred scopes.
- [x] Black-box verifier tests distinguish deferred dependencies, self-reference, and genuinely unknown identities.

## Notes
Implementation uses the existing split `ValueScope` as the semantic owner of
availability. It does not infer evaluation timing from `ValueKind`, and it does
not duplicate the callable dependency analysis in the expression verifier.

## Close Notes
Added `InitializationOrderViolation(initializer, dependency)` and made
`ValueScope` classify references as available, deferred, or absent. Deferred
top-level values carry their eager initializer by construction, so the verifier
cannot silently fall back to `UnknownValue`. The callable fixed-point analysis
now returns named `InitializationOrderFailure` records and reports the same
diagnostic as direct deferred references. Black-box tests cover direct,
transitive-callable, function-valued eager, self-reference, and truly unknown
cases; interpreter error rendering exposes both ends of the ordering edge.
