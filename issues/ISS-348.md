# ISS-348: Restore the semantic contract in lane link help

## Metadata

- Status: closed

## Description
After argparse took ownership of generated command usage, `lane link --help`
describes its positional inputs only as module object artifacts. It no longer
tells users that every module reachable from the selected entry must be
supplied. Omitting that semantic constraint turns a normal usage requirement
into a later missing-module diagnostic.

## Design
Keep argparse as the owner of syntax and usage rendering, but add the reachable
module requirement to the command or positional-argument explanatory text. Do
not restore a hand-written usage block or duplicate option formatting.

## Acceptance Criteria
- [x] `lane link --help` states that all modules reachable from the selected
      entry must be supplied.
- [x] The note appears in normal subcommand help and in argparse-rendered link
      argument failures where the command description is shown.
- [x] A built-executable black-box test pins the semantic note without
      duplicating the complete generated usage layout.
- [x] Existing link diagnostics and artifact behavior are unchanged.
- [x] `moon test --target native`, the CLI integration gate, and
      `git diff --check` pass.

## Close Notes

The `objects...` positional argument now states the semantic input-closure
requirement directly: callers must supply one object artifact for every module
reachable from the selected entry. Argparse remains the sole owner of usage,
option, and argument-failure rendering, so both normal help and parser failures
present the same requirement.

`tools/check-lane-cli-help.sh` runs the built executable and checks only this
semantic sentence in both paths. The integration gate builds Lane once and
passes that executable to the examples, CLI-help, and LSP checks.
