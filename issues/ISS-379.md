# ISS-379: Centralize Wasm function and table identity allocation

## Description
Wasm runtime functions, helper functions, bytecode functions, Runtime Import
adapters, shape destructors, callable-table entries, cleanup, and entry wrapper
derive their identities from several independent hard-coded lists and offset
formulas. Runtime function count, helper count, Wasm bases, table bases,
`import_count + FunctionId - 1`, append order, and provenance order must all
remain synchronized manually.

## Design
Build one `WasmFunctionCatalog` before body emission. Declare every imported or
defined function by a typed role, including dynamic `DestroyShape(index)` roles,
and assign its Wasm function handle, optional table slot, function type,
provenance, and deterministic emission order exactly once. Allow forward
references so bodies consume handles without requiring prior append order.

The emitter materializes the catalog into a Wasm Module; it does not allocate
semantic identities. Static-image layout, callable-table construction, runtime
bodies, helpers, lifecycle, exports, and metrics all consume catalog handles.
No internal compiler code should calculate function or table indices from raw
counts and offsets.

## Acceptance Criteria
- [x] One catalog contains every internal import, physical import, bytecode
      function, Runtime Import adapter, runtime function, helper, optional
      cleanup function, and entry wrapper.
- [x] Wasm function index, table slot, function type, provenance, and emission
      order are allocated together by the catalog.
- [x] Runtime/helper bodies and direct calls use typed handles rather than raw
      `Int` indices or offset formulas.
- [x] `runtime_function_count`, helper base/count fields, `wasm_indices()`, and
      bytecode-function index arithmetic are deleted.
- [x] Catalog validation rejects duplicate roles, missing referenced roles,
      incompatible function types, and table entries without callable bodies.
- [x] Structured tests inspect the complete small catalog; interpreter/JIT
      conformance and persisted bytecode behavior remain unchanged.
- [x] Explore Wasm provenance and scale consume the same catalog facts.
- [x] `moon info`, `moon fmt`, `moon check --target native --warn-list +73`, and
      `moon test --target native` pass.

## Close Notes

`WasmFunctionCatalog` now assigns imports, Bytecode-backed definitions,
Runtime Import adapters, runtime functions, helpers, shape destructors,
optional global cleanup, and the entry wrapper before body emission. Each entry
owns its typed handle, physical function type and interned type index,
declaration kind, optional callable-table slot, provenance, and emission order.

Wasm bodies, entry lifecycle, static layout descriptors, callable-table
materialization, exports, and observations consume catalog handles. The old
runtime/helper index records, callable-table plan, count/base fields, raw
`FunctionId` offset arithmetic, and emitter-owned provenance were deleted. The
catalog validator and one complete structured white-box snapshot cover the
otherwise private completeness invariant; public Wasm compilation and execution
tests remain the behavioral test surface.

Verified with `moon info`, `moon fmt`,
`moon check --target native --warn-list +73`,
`moon test modules/loisvm/wasm --target native` (83/83), and
`moon test --target native` (1744/1744).
