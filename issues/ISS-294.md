# ISS-294: Unify CPS callable declarations and implementations around one shape

## Description
CPS callable metadata and callable expressions are assembled along separate
paths. ISS-293 established that this split is not the cause of its dictionary
pair mismatch, but it still permits a future lowering branch to construct a
declaration type and implementation from different decisions.

## Design
Represent one function occurrence with a `CpsCallableShape` containing its
source and target types, answer and residual parameters, context parameter
types, value parameter types, and result type. Both the committed declaration
and the `TypeLambda`/`Function` implementation consume that shape. Where a
consuming position provides an expected type, derive the shape from that type;
otherwise synthesize the source type once.

This is a consistency refactor, not part of the higher-kinded companion fix in
ISS-293. Do not use shared quantifier identities or a structural rewrite cache
as a substitute for one explicit shape.

## Acceptance Criteria
- [x] Each CPS callable occurrence has one `CpsCallableShape` used by both its
      declaration and implementation.
- [x] Expected-position and synthesized-position callables use the same shape
      construction rules.
- [x] Focused tests fail at the originating binding if declaration and
      implementation construction diverge.
- [x] `moon check`, focused CPS tests, and `moon test --target native` pass.
