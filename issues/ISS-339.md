# ISS-339: Preserve contextual parameter identity in offer diagnostics

## Metadata
- Type: bug
- Status: closed
- Priority: 2
- Labels: area/typecheck, area/diagnostics, area/basic, contextual-offers, tests, agent
- Assignee: codex
- Created: 2026-08-08
- Updated: 2026-08-10
- External ref: modules/lanec/typecheck/contextual_call.mbt, modules/lanec/typecheck/core.mbt, ../basic/test/eff/write.lane

## Description
Direct-call contextual insertion still owns each omitted `auto` parameter's
name when it attempts offer lookup, but it passes only the required type into
`required_contextual_offer`. `MissingContextualOffer` and
`AmbiguousContextualOffer` therefore retain the type but lose the parameter
identity before diagnostic rendering.

The Basic `assert_equal` reproduction has two omitted contextual parameters.
Current diagnostics report requirements for `(List[I64]) -> String` and
`Equal[List[I64]]`, but do not say that these are `debug_impl` and
`equal_impl`. This is especially opaque because transparent aliases make the
first requirement render as a plain function type.

This is a diagnostic-data defect, not a contextual-resolution defect. Lane
must continue to match exact visible offers and must not recursively search
generic provider functions to hide the missing arguments.

## Design
Represent a contextual requirement with both its required type and its source
site. A direct-call site carries the checked auto parameter name; derive and
other non-parameter sites retain their own domain-specific diagnostics.
Lookup remains a pure exact-match operation. The caller converts a missing or
ambiguous lookup into a diagnostic while it still owns the requirement site.

Render direct-call failures in terms of the parameter, for example
``auto offer parameter `debug_impl` requires `(List[I64]) -> String` ``, and
make the help name the explicit labeled argument `debug_impl=`. Apply the same
identity rule to missing and ambiguous results.

## Acceptance Criteria
- [x] Missing direct-call contextual-offer diagnostics include the exact auto parameter name and required type.
- [x] Ambiguous direct-call contextual-offer diagnostics include the exact auto parameter name, required type, and existing candidate facts.
- [x] Diagnostic help names the labeled argument that can be supplied explicitly.
- [x] Derive evidence and other non-call contextual diagnostics keep their domain-specific identity and wording.
- [x] Exact visible-offer matching remains unchanged; the fix introduces no recursive provider search or generic inference from the offer set.
- [x] A black-box compiler diagnostic test covers two missing contextual parameters with different names and types in one call.
- [x] A committed invalid example using the pinned Basic `Debug`, `Equal`, and
      `List` types identifies `debug_impl` and `equal_impl` correctly while
      generic offers remain exact-only.
- [x] `moon info`, `moon fmt`, and `moon test --target native` pass.

## Notes
- 2026-08-08: Reproduced with the current development compiler by removing the explicit `equal_impl=` and `debug_impl=` arguments from `Basic`'s write-effect test. Two E3013 diagnostics retained the types but neither parameter name.
- 2026-08-08: Reopened because the pinned Basic revision still supplies
  `summon_via[Equal, List, I64]()` explicitly, so the claimed real-library
  reproduction is not preserved by any committed gate.
- 2026-08-10: The pinned Basic test suite no longer contains the historical
  two-auto-parameter `assert_equal` call. Its `assert_eq!` operation takes
  equality evidence explicitly, so removing `summon_via` would change the
  program rather than reproduce this diagnostic defect. The acceptance case
  now records the same boundary honestly through a Lane invalid example that
  imports the real Basic types and generic offers.

## Close Notes

Contextual lookup already preserves direct-call parameter identity through the
structured `AutoParameter` requirement site, while structural derivation keeps
its separate diagnostic identity and exact visible-offer matching remains
unchanged.

Added `examples/invalid/89_basic_contextual_parameter_identity.lane`, which
imports the pinned Basic `Debug`, `Equal`, and `List` types together with their
generic providers. The built Lane executable now verifies that the two omitted
arguments are reported as `debug_impl` requiring `(List[I64]) -> String` and
`equal_impl` requiring `Equal[List[I64]]`, including their explicit labeled
argument help.

Verified the fixture directly with the release Lane executable, `moon info &&
moon fmt`, `moon test --target native` (1601/1601), the complete
`tools/check-lane-integration.sh` gate against pinned Basic revision
`b5a1a651c931`, and `git diff --check`.
