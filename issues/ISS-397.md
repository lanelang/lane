# ISS-397: Make exported Wasm runtime services layout-valid

## Metadata
- Type: bug
- Status: closed

## Description
The Wasm target unconditionally exports `lane.runtime.string.new` and
`lane.runtime.host_object.new`, while `StaticImage` uses zero as the sentinel
for an absent ByteSequence or Reference layout. The public Physical Program
compiler accepts a scalar program with neither layout, so either exported
service can construct a reference whose layout ID is zero. The module is
syntactically valid Wasm but the service contract is not valid.

ISS-396 intentionally retained these existing exports as explicit catalog
roots; it exposed rather than created this independent runtime-service ABI gap.

## Design
Make runtime-service availability and its required static layout one certified
fact. Do not emit a service backed by a sentinel layout ID and do not silently
add every service layout to every scalar program.

The preferred direction is to export String and host-object construction only
when a retained runtime import can return the corresponding value kind, and to
make the Wasmoon loader request only services certified by that import
contract. Before implementation, reconcile ADR-0083's unconditional String
wording with its broader “may export explicitly designated services” rule and
record whether service presence is an artifact capability.

## Acceptance Criteria
- [x] No exported runtime service can construct a value with layout ID zero.
- [x] Service roots, exports, static layouts and loader requirements consume one
      certified capability fact.
- [x] A scalar module omits unused services and their layouts/support.
- [x] String-result and Opaque-result imports expose and execute exactly the
      service they require.
- [x] ADR-0083 and runtime ABI documentation match the implemented capability
      contract.
- [x] Public compile/instantiate tests cover scalar, String and Opaque cases.

## Notes
- 2026-08-27: Discovered while making Wasm support reachability exact. The
  catalog correctly treats current exports as roots, but cannot make an export
  semantically valid when its required layout is absent.
- 2026-08-28: Started implementation. The shared Wasm ABI package will own the
  runtime-service universe and the service requirements of both retained user
  imports and retained internal imports. The Wasm catalog will certify those
  requirements against physical layouts; emission and loading will consume the
  certified result without unconditional exports or lookup fallbacks.

## Close Notes

- `lane_runtime/wasm_abi` now owns the complete runtime-service universe: stable
  names, Wasm function types, and the retained user/internal import results that
  require each service.
- The Wasm function catalog derives service demands from its retained import
  closure, certifies each demand against one nonzero Physical Program layout,
  and is the only source for service roots and exports. Scalar and input-only
  imports no longer retain construction services or their support.
- The Wasmoon loader derives the same required capability set from its already
  validated import contracts, rejects missing, extra, or mistyped exports, and
  caches certified function indices. Per-call export-name searches were
  removed.
- Public regressions cover scalar, String-result, Opaque-result, String/Opaque
  input-only, invalid layout, and invalid loader-contract cases. The scalar
  Explore fixture shrank from seven Wasm functions and 224 instructions to four
  functions and 53 instructions.
- Verified with `moon info`, `moon fmt`, `moon check --target native
  --deny-warn`, 1747/1747 native tests, release Lane build, Basic 12/12, and the
  full valid/invalid examples gate.
